## APP-04: recovery command and status preservation

`OtpService.complete` (`services/identity-api/src/auth/otp.service.ts:207`) locks the challenge and then at `:224` directly updates account password, status and token version. `database/runtime-grants.sql:353` grants Identity SELECT on accounts; `:357` grants challenge mutation; account credential changes otherwise use a narrow security-definer function such as migration0007's legacy-password upgrade.

A separate risk must be retained when designing the fix: OTP start filters active/pending_reset accounts (`otp.service.ts:73`), but verify/complete do not recheck current account status or `disabled_until`. Completion unconditionally sets `status='active'`. Admin disable (`0027_super_admin_foundation.sql:451`) revokes sessions but does not invalidate OTP challenges. An issued completion token can therefore remain pending after a disable. This is **not a proven deployed authorization bypass** under the correct runtime role, which lacks the account UPDATE privilege. Granting broad UPDATE would expose the status-preservation defect.

Smallest safe correction proposal: additive migration0029 with a narrowly granted recovery command using locked challenge/account rows, exact purpose/token binding, current eligible account status and disabled-until checks, atomic consume/password/token-version/session revocation/assurance/semantic audit; minimal service call replacement; exact-role positive, expired/replayed/wrong-purpose, disabled-after-start/verify and concurrency regression tests. Keep generic account UPDATE denied. Do not misuse the old-password upgrade function. Preserve applied migration hashes.

This changes schema compatibility and the exact28-file release/migration contract. It cannot be represented as approved SHA a709e643. Requires reviewed additive migration and candidate release/ledger/rehearsal updates; no recovery source implementation was made during this audit. Focused runtime proof is recorded in the supplement below.
