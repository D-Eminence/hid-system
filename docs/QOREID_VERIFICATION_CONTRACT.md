# QoreID verification contract

**PR #5 state:** implemented with deterministic, sanitized fixtures; provider calls remain disabled by default. The project owner has empirically verified the body-free NIN-only call with an entitled QoreID sandbox account and observed HTTP 200. This PR's automated tests use fixtures; no production verification, deployment, or live database migration has been performed. No sandbox credential or identity data is stored in the repository.

QoreID supplies external identity evidence. HID owns the account, contact verification, password, patient identity, Health ID, organization approval, and administrator setup.

## Public patient enrollment

`Get your Health ID` opens `/patient/enroll`. The browser submits only an 11 digit NIN and a Turnstile token to `POST /api/v1/identity/patient-enrollments`; it cannot submit names, birth date, gender, address, or a QoreID phone value. Identity validates exactly 11 numeric digits and sends only the NIN through a separate NIN-only adapter operation. QoreID performs the identity/details matching. HID accepts the authoritative identity result only when `summary.nin_check` is the string `verified`, `status.state` is `complete`, `status.status` is `verified`, and `nin.nin` equals the submitted NIN. It validates and normalizes the returned identity fields rather than accepting applicant-supplied demographics. A failed, mismatched, incomplete, or malformed response stops enrollment. The entitled sandbox response also confirmed a numeric top-level `id` as the provider transaction/reference identifier. HID requires that field, stores its safe normalized reference, and fails closed if it is absent or malformed; the actual sandbox value is not recorded here.

**Entitled sandbox verification:** The project owner sent `POST https://api.qoreid.com/v1/ng/identities/nin/{11-digit-NIN}` with a sandbox bearer token and **no request body**. QoreID returned HTTP 200 with the success fields, exact returned NIN, and numeric top-level `id` above. The observed response also contained `nin.firstname`, `nin.lastname`, `nin.middlename`, `nin.phone`, `nin.gender`, `nin.photo`, `nin.birthdate`, and the nested `nin.residence.address1`, `nin.residence.town`, `nin.residence.lga`, and `nin.residence.state`. This establishes the body-free transport and response shape for the entitled sandbox account. [QoreID's published NIN-with-NIN documentation](https://docs.qoreid.com/docs/nin-with-nin) shows the same path with first and last names in a request body; the sandbox result establishes that this entitled NIN-only variant accepts a body-free call. HID must not invent name inputs to fill the published request. Successful QoreID details matching is the authoritative identity verification for enrollment; the response has no separate holder-possession or consent-proof field, and HID does not require one. The later HID OTP proves control of the selected account contact only. `QOREID_NIN_ONLY_ENROLLMENT_ENABLED=false` remains the default, including when general `QOREID_ENABLED=true`, until the remaining release and security gates are cleared.

The adapter normalizes the observed registry fields as `nin.nin` → `nin`, `nin.firstname` → `firstName`, `nin.lastname` → `lastName`, `nin.middlename` → `middleName`, `nin.birthdate` → `dateOfBirth`, `nin.gender` → `gender`, `nin.phone` → `phoneNumber`, and `nin.photo` → `photo`. It maps `nin.residence.address1`, `nin.residence.town`, `nin.residence.lga`, and `nin.residence.state` into HID's internal `residence` object, and uses `nin.residence.address1` as the internal flat `address` compatibility field. The provider response is not parsed from a top-level `residence` path. Optional returned fields must be valid when present. These registry values are server-only and are encrypted in the pending enrollment profile; the QoreID phone does **not** select or verify an HID account contact. The patient independently chooses one phone or email for HID's OTP.

**A record without a date of birth or gender (ADR-061; D-Eminence/hid-system#82, migration 0092, not deployed).** QoreID may return a verified NIN record with only the name, the NIN and its reference. In the enrollment binding only `nin.nin` (equal to the submitted NIN), `nin.firstname` and `nin.lastname` are required. `nin.birthdate` and `nin.gender` are optional: absent, `null` or the empty string leaves the key out of the binding and of the stored profile (never `null`); a value that is present but does not parse (a date that is not `DD-MM-YYYY` or `YYYY-MM-DD` on the calendar, from 1800 to today, or a gender outside the mapped values) still fails closed with `502 QOREID_PROVIDER_RESPONSE_INVALID`. The service then accepts a date of birth only from 1900-01-01 to today, as before. Progress answers before activation name the missing fields in `requiredProfileFields`, and the patient enters them with the password (`INTERFACE_CONTRACT.md`). A field the record gives can never be replaced: Identity refuses it (`400 ENROLLMENT_PROFILE_FIELD_VERIFIED`) and so does the activation command. The canonical patient's `dob` and `gender` hold the record's value or the entered one; the authoritative profile stays exactly what QoreID returned, so a value the authoritative profile lacks was self-reported, and the activation audit event lists the entered field names in `selfReportedFields` (never values). The signed-in progressive NIN binding (Portal "Verify NIN", `QoreIdNinBinding`) is unchanged: it still compares the patient's date of birth with the registry's. When QoreID returns no birth date it refuses: `not_verified` if QoreID marks the date as not matching (`fieldMatches.dob` false), otherwise `502 QOREID_PROVIDER_RESPONSE_INVALID`. That is an open follow-up.

**The lookup proves only that the NIN exists (ADR-062; BRANCH:launch/nin-ownership-proof, migration 0093, not deployed).** The body-free lookup does not prove that the caller holds the NIN. Ownership comes from a separate proof: a six-digit code sent by SMS to the phone the NIN record lists (`nin.phone`), or an in-person check at a participating facility (ADR-063, BRANCH:launch/facility-assisted-registration, 0094; off until a facility is designated). The in-person check compares the names and date of birth on an original photo ID with the record blindly; staff never see a record value. HID generates the code and Termii carries it; QoreID offers no OTP or phone-ownership product. `nin.phone`, `nin.photo`, `nin.residence` and each residence field are absent when `null` or `''`. A `nin.phone` that is not usable text (a number, an object, control characters, more than 30 characters) is left out, never a `502`. Identity keeps a phone only when it normalizes to `+234` and 10 digits (from `0` + 10 digits, `234` + 10 digits or `+234` + 10 digits, with spaces, hyphens or brackets removed); otherwise, or when the record shows an age under 18, the online route is closed for that enrollment. The phone is never returned to the browser or logged, and only HMAC digests of it are stored. Whether production records carry a usable `nin.phone`, what it means, when it was captured, whether a SIM change is flagged and whether HID may text it are unconfirmed (DEP-1); the online route works only where the lookup returns a usable phone. Production refuses the online route until the facility route ships (ADR-063); with 0094 it runs only with the facility route on. Whether the NIN already has a Health ID is answered only after the proof.

On success, migration `0051_public_patient_enrollment.sql` stores a single pending enrollment keyed by the same NIN lookup HMAC used by governed NIN bindings. It stores NIN and the normalized returned registry profile encrypted at rest. It does **not** create an account, patient, or HIDCode. Existing active NIN bindings, duplicate pending NINs, concurrent starts, and replayed idempotency keys are rejected or resumed without a second HID. *Superseded by ADR-062 (0093):* the NIN is no longer unique among enrollments, each start with a new key stores its own enrollment at `verify_holder`, a holder proof removes the NIN's other unfinished enrollments, and a bound NIN is answered only after that proof; one proven enrollment per NIN is kept by a unique index.

**Gate before registry lookups (ENR-4 step 1; D-Eminence/hid-system#68, not deployed).** After the Origin, Turnstile, signed-in-session and input checks, start asks the QoreID gate (`PublicPatientIdentityProvider.assertAvailable`: `QOREID_ENABLED`, `QOREID_NIN_ONLY_ENROLLMENT_ENABLED`, then the runtime pause of `qoreid`/`patient_nin`) before it charges a rate bucket or reads whether the NIN is bound or pending. While the gate is closed every NIN gets the same `503 QOREID_DISABLED`, `503 QOREID_NIN_ONLY_DISABLED` or `503 INTEGRATION_PAUSED`, a same-key resume included; `GET /current` still answers with the cookie. Before 0093, with the gate open, a bound or pending NIN was `409 NIN_ALREADY_REGISTERED` before QoreID was asked. From 0093 (ADR-062) start never reads whether the NIN is bound or pending and never answers `409 NIN_ALREADY_REGISTERED`; only a correct holder code does. From 0093 the start also answers `503 PATIENT_REGISTRATION_NOT_OPEN` before this gate when no holder route is open. `verifyNin` keeps the same gate checks.

**Registration not open (FE-4; D-Eminence/hid-system#68, not deployed).** `503 QOREID_DISABLED` and `503 QOREID_NIN_ONLY_DISABLED` carry the detail "New Health ID registration is not open yet. If you already have a Health ID, sign in." (a `PublicDetailProblem`, which Identity's problem filter does not replace with its generic 5xx detail); the adapter's own NIN-only refusal uses the same sentence. From 0093 a start with no holder route open answers `503 PATIENT_REGISTRATION_NOT_OPEN` with the same detail before the QoreID gate; with every flag at its default, and in production until the facility route ships (ADR-063), that is what Identity answers every start; through the gateway on `main` a browser still gets `503 UPSTREAM_UNAVAILABLE` until ADR-055 (D-Eminence/hid-system#72) passes upstream errors through. `GET /api/v1/identity/patient-enrollments/availability` answers `{ "open": boolean }` from the same checks (the enrollment keys, then `PublicPatientIdentityProvider.isAvailable`, which is `assertAvailable` as an answer), so a client can say that registration is not open before it asks for a NIN and a Turnstile token (`INTERFACE_CONTRACT.md`).

**QoreID lookup quota (IP-1; migration 0085).** Public enrollment has no account to charge, so the account-scoped 0049 `patient_nin` quota cannot apply. Immediately before each NIN lookup, after the gate, the provider charges `platform.consume_public_patient_nin_quota`: a keyed HMAC of the client network (the request IP Identity derives; an IPv4 address, or the /64 of an IPv6 address, so rotating addresses inside one allocation does not reset it) is counted per hour and per day, and every lookup counts against one platform-wide daily cap. The limits are `PATIENT_ENROLLMENT_QOREID_NETWORK_HOURLY_MAX` (default 5), `PATIENT_ENROLLMENT_QOREID_NETWORK_DAILY_MAX` (15) and `PATIENT_ENROLLMENT_QOREID_DAILY_CAP` (200; the owner sets it from the QoreID contract). A refusal is committed with its audit event (`identity.public-patient-enrollment.nin-lookup-quota`, outcome `denied`, the exhausted limit and the network digest; no NIN or address) and answered `429 VERIFICATION_QUOTA_EXCEEDED` before any request leaves; QoreID is not called. A resume, a duplicate and every earlier refusal are never charged. Until the edge delivers the real client address (IP-1), every client behind one load balancer node shares one network budget.

The user then chooses exactly one HID account contact: phone **or** email. This contact is independent of QoreID's phone evidence. A purpose- and enrollment-bound six digit OTP is sent through the existing Notification API, with expiry, attempt limit, cooldown, rate limits, single use, and an audit trail. Only after that OTP succeeds can the user set a password. A single database transaction then creates the active account, canonical patient, NIN binding, authoritative profile, assurance state, HIDCode, and semantic audit event. Repeating activation on an active enrollment (a lost response) returns the same HIDCode and ignores the password, for 15 minutes after activation (decision N2(b)); it computes no password hash, because the database command returns before it would read one. After those 15 minutes the replay, like `GET /current`, is `404 ENROLLMENT_NOT_FOUND` without the HIDCode, and the activation command refuses it too (0085). A contact proof is valid for activation for 30 minutes (N2(c)): with an older one, activation clears the proof and the contact, sends the enrollment back to the contact step and answers `409 ENROLLMENT_CONTACT_REVERIFY_REQUIRED`, and the activation command refuses such an enrollment as well (0085). Activation attempts of one enrollment share a budget: every attempt that passes the cookie and stage checks is counted, whatever its outcome (a first activation, a replay, or an attempt that then fails, such as a `503` during reconciliation), in an enrollment-scope rate bucket of its own (not the contact step's). The attempt after `OTP_RATE_MAX_REQUESTS * 3` (default 15, the contact step's per-enrollment size) within `OTP_RATE_WINDOW_SECONDS` (default 900) is `429 ENROLLMENT_RATE_LIMITED`, before any password hash or activation command. The patient can sign in with email or the issued HIDCode; normal sign-in never repeats NIN verification. Recovery sends a code to the verified HID account contact, including SMS for a phone-only account.

The enrollment cookie is HttpOnly, Secure in deployed environments, SameSite Strict, and scoped to the enrollment route. Mutations require an allowed Origin; starting also requires server-side Turnstile validation. The browser stores only a retry UUID across refreshes, never a NIN, provider payload, OTP, or secret. Pending state can be resumed through `GET /current`. Every successful activation response, a replay's included, expires the cookie (D-Eminence/hid-system#68, not deployed). If that response is lost, the cookie still lets `GET /current` answer `active` with the HIDCode, and an activation replay return it, on that device for 15 minutes after activation; then both answer `404 ENROLLMENT_NOT_FOUND`. Every staff or patient sign-in, refresh and sign-out on the device expires the cookie (`INTERFACE_CONTRACT.md`, "Auth session contract"); the signed-in patient reads the HIDCode from `GET /api/v1/identity/me`. Identity's request audit records success/failure without registry fields or codes.

Wrong contact codes also spend one failure budget per recipient (the keyed HMAC of the chosen contact), across all its challenges and enrollments: a resend, or another enrollment naming the same contact, does not bring more guesses. It is never keyed by client IP. By default the fifth wrong code within 15 minutes blocks that recipient for 15 minutes (`PATIENT_ENROLLMENT_CONTACT_FAILURE_MAX`, `PATIENT_ENROLLMENT_CONTACT_FAILURE_WINDOW_SECONDS`), the budget the platform MFA code already uses. While it is blocked, every code for that recipient is refused, a correct one too, with the usual `422 OTP_INVALID`, before it is compared and without counting it, and the contact step answers `429 ENROLLMENT_RATE_LIMITED` and sends no code. The refusal neither counts against nor invalidates the challenge. A refusal for an unknown or expired challenge spends nothing. The counter is a row of `auth.otp_rate_limits` (scope `recipient`, its own HMAC domain over the recipient HMAC), read, compared and counted under that bucket's transaction lock after the enrollment and challenge row locks; no other challenge is written. This comes from D-Eminence/hid-system#61 and is not yet deployed; the threshold is an open product decision (release checklist §2).

Enrollment start and the contact step are also limited per client network, an IPv4 address or an IPv6 /64 (D-Eminence/hid-system#65): start at `PATIENT_ENROLLMENT_START_RATE_MAX_REQUESTS` (default 5) and the contact step at `OTP_RATE_MAX_REQUESTS * 3` (default 15) per `OTP_RATE_WINDOW_SECONDS` (default 900), each answering `429 ENROLLMENT_RATE_LIMITED` beyond it. The client address is the one the Cloudflare Worker took from `CF-Connecting-IP` and the gateway forwarded from the VPC; before that change it was a load balancer node's, shared by every client. A start or contact step without a usable client address, or in production with an address inside `TRUST_PROXY_CIDRS` (one of the platform's own proxies), answers `503 ENROLLMENT_RATE_LIMIT_UNAVAILABLE` before any database work, rather than charge a bucket every client would share. The start limit is a product threshold: mobile carrier-grade NAT can put many patients behind one IPv4 address.

**Database-backed HTTP verification (local and synthetic only):** `services/identity-api/scripts/verify-patient-enrollment-runtime.mjs` runs public enrollment through activation and sign-in for two new patients, then session, refresh, OTP password recovery and sign-out for the first, then the contact-code failure budget for a third enrollment, then a record with only the name whose patient enters the date of birth and gender (ADR-061), then the enrollment gate, the two windows of decision N2 (activating the third enrollment after a new contact proof), the QoreID lookup quota and the availability read (FE-4). It refuses to run outside the synthetic migration rehearsal; `scripts/tuf-staging-migration-rehearsal.mjs` runs it after `verify-patient-runtime.mjs`. It works on a disposable copy of the rehearsal's `hid_rehearsal` database, which it drops afterwards, and asserts that its API connection is `hid_identity_api_runtime`. It serves the real `PatientEnrollmentController`, `AuthController`, `OtpController` and `PatientSelfController` and their services over HTTP from a Nest test module, with the validation pipe, problem filter, global `SecurityGuard` and `AuditInterceptor` that `AppModule` and `main.ts` use; it does not boot the full `AppModule`. It mounts `main.ts`'s no-store middleware but omits its Helmet and CORS middleware, uses Nest's default body parser instead of `main.ts`'s 256 KiB JSON parser, sets a random correlation id instead of running `CorrelationMiddleware`, and injects the QoreID adapter configuration directly rather than reading `QOREID_BASE_URL` and `QOREID_TIMEOUT_MS`. No external service is called. The real `QoreIdVerificationAdapter` and `QoreIdPublicPatientIdentityProvider` receive an in-process stub of QoreID's token and NIN-only endpoints, which returns a reduced form of the entitled sandbox response (numeric `id`, `summary.nin_check`, `status.state`/`status.status`, and `nin.nin`, `firstname`, `lastname`, `birthdate`, `gender`, with no `middlename`, `phone`, `photo` or `nin.residence`) for three invented NINs and the same without `birthdate` and `gender` for a fourth, all of which the run enrolls, and a `not_verified` result for a fifth. Cloudflare Siteverify is replaced by a stub whose token encodes the outcome, and `NotificationOtpClient` by a stub that records each code. Any other request through `fetch`, any QoreID path other than the token and NIN-only endpoints, and any NIN the stub does not know, fails the run. The verifier sets `QOREID_ENABLED`, `QOREID_NIN_ONLY_ENROLLMENT_ENABLED`, required Turnstile and fresh random NIN and contact keys only in its own process. QoreID starts paused in the integration settings, as migration `0047` seeds it; the verifier enables it itself as the database owner in its disposable copy only, standing in for an administrator.

It checks that:
- enrollment start refuses a missing or foreign `Origin`, a wrong Turnstile action (in the body or the token) or a replayed token, a missing `Idempotency-Key` and a malformed NIN before QoreID is called or anything is stored;
- start answers `503 INTEGRATION_PAUSED` while QoreID is paused and `422 NIN_NOT_VERIFIED` for a negative check, creating no enrollment record;
- a successful start calls QoreID once, keeps no clear NIN in `nin_ciphertext` or `profile_ciphertext` and stores the last four digits in `nin_last4`, returns no NIN, name, birth date, patient id or HIDCode, and sets a host-only `HttpOnly; Secure; SameSite=Strict` cookie scoped to `/api/v1/identity/patient-enrollments`;
- a same-key replay calls QoreID no more and returns the same cookie, another key for the same NIN is a new enrollment at `verify_holder` (from 0093; before, `409 NIN_ALREADY_REGISTERED`), the same key for another NIN is `409 IDEMPOTENCY_KEY_REUSED`, and `GET /current` with no cookie or an altered one is `404 ENROLLMENT_NOT_FOUND`;
- the contact step refuses a malformed email (`400 ENROLLMENT_CONTACT_INVALID`), normalizes the email, delivers a `SIGNUP_VERIFY` code for the issued challenge, enforces the resend cooldown (`429 OTP_RESEND_COOLDOWN`), shows the contact masked (`p•••@example.invalid`) in `GET /current`, refuses a wrong code (`422 OTP_INVALID`) and activation before verification (`409 ENROLLMENT_STAGE_INVALID`), and accepts the code once;
- activation refuses a too-short password (`400 VALIDATION_FAILED`), then creates exactly one active account with a verified email and one patient with the QoreID name and birth date, source system `hid-public-qoreid-enrollment` and a new HIDCode; a replay returns the same HIDCode and ignores a second password; replays succeed up to `OTP_RATE_MAX_REQUESTS * 3` calls of that enrollment and the next is `429 ENROLLMENT_RATE_LIMITED` without the HIDCode, all counted in one enrollment-scope bucket;
- an enrolled email is refused to a new enrollment (`409 CONTACT_ALREADY_REGISTERED`); from 0093 a start for an enrolled NIN answers `verify_holder`, and only its correct holder code answers `409 NIN_ALREADY_REGISTERED` with the recovery text, expiring the cookie and deleting that enrollment;
- a phone-only enrollment normalizes `0803…` to `+234…`, delivers by SMS and activates an account with no email;
- patient sign-in gives a wrong password and an unknown account the same `401` body apart from `instance` and `correlationId`, refuses another Turnstile action, and signs in by email in any case or by HIDCode, including the phone-only patient; the email sign-in's cookies are host-only, Secure and Strict (all but the CSRF cookie `HttpOnly`) and it expires `hid_enrollment` on `/api/v1/identity/patient-enrollments`, its JSON body carries no tokens and its actor no workforce roles, permissions or facilities;
- each session reads only its own profile and HID through `GET /api/v1/identity/me`, without NIN or account id, and the EHR self-authorization route names only that session's patient;
- refresh with the CSRF token rotates the session for the same patient, expires `hid_enrollment`, and the previous session is refused;
- OTP password recovery answers known and unknown accounts in the same shape; within the resend cooldown a repeat start answers the same `challengeId` for an unknown identifier and for the account's email in another case, sending no code, and the account's HID gets a new `challengeId` and no code (D-Eminence/hid-system#55); recovery completes once (`403 OTP_INVALID_OR_EXPIRED` when repeated), ends existing sessions and replaces the password;
- sign-out without the CSRF token is refused and ends nothing; with it, it ends only that sign-in and expires `hid_enrollment`, while the same patient's other sign-in and the other patient stay signed in;
- every successful `api.identity.patient-enrollment.start` (three, the replay included) and `api.identity.patient-enrollment.activate` (one per patient plus each replay within the budget) is audited as a success with status `200`, refusals of each as failures, and `identity.public-patient-enrollment.activated` once per new patient; no audit detail contains either enrolled NIN, the first patient's original or recovered password, or its contact code;
- the contact code has one failure budget per recipient across its challenges and networks: after five wrong codes for a third enrollment's email (three on a challenge, two on its resend, each from another synthetic network) its correct code is `422 OTP_INVALID` and leaves the challenge open and uncounted, the five failures are one blocked `recipient` row of `auth.otp_rate_limits` keyed by the recipient HMAC in its own domain (no other rate row is written), the contact step answers `429 ENROLLMENT_RATE_LIMITED` and sends no code, and once the owner lifts the block the same code verifies;
- the first activation response and a replay's each expire `hid_enrollment` on its path (D-Eminence/hid-system#68);
- while QoreID is paused (`503 INTEGRATION_PAUSED`) and while `QOREID_NIN_ONLY_ENROLLMENT_ENABLED` is switched off in its own process (`503 QOREID_NIN_ONLY_DISABLED`), a bound NIN, a pending one and one the run never used get the same answer apart from `instance` and `correlationId`, QoreID is not called and no enrollment rate bucket or row is written;
- `GET /current` shows the first patient's HIDCode after activation, and once the owner moves the activation 16 minutes back, `GET /current` and an activation replay answer `404 ENROLLMENT_NOT_FOUND` without it;
- once the owner moves the third enrollment's contact proof 31 minutes back, activation answers `409 ENROLLMENT_CONTACT_REVERIFY_REQUIRED`, the enrollment is back at `verify_contact` with its contact and proof cleared and no patient is created; proving the contact again activates it, and that response expires the cookie;
- the QoreID lookup quota counts exactly the lookups made (none for the replay, the duplicates or the gated refusals); five lookups from five addresses of one IPv6 /64 are made and a sixth address of that /64 is `429 VERIFICATION_QUOTA_EXCEEDED` without a lookup, while another /64 is still served; with the owner setting the platform counter to the daily cap, a lookup from a fresh network is `429` without a lookup; each lookup is audited as a success and each refusal as `denied` with `network_hour` and then `platform_day`;

It does not exercise the production refusal of the NIN-only flag (unit tests cover it), or the `503 ENROLLMENT_RECONCILIATION_REQUIRED` gate, which keeps enrollment closed while a legacy import run is staged or running, while promoted legacy patients lack a reconciled NIN crosswalk, or while older contact lookups lack the applied rekey (see [the migration runbook](MIGRATION_RUNBOOK.md)); the rehearsal runs the verifier before it stages any legacy source. Nor does it exercise OTP expiry or the per-challenge attempt limit, the start and contact rate limits (it spreads requests across synthetic networks; it does exhaust the activation budget, the contact-code failure budget and the lookup quota), the daily per-network lookup limit, concurrent starts, or Google onboarding binding (`POST /google`). The windows of N2 are reached by moving stored times back as the database owner, not by waiting. Because the stub's response is reduced, the `middlename`, `phone`, `photo` and `nin.residence` mapping described above is not exercised either.

## QoreID access token lifetime

QoreID directly confirmed that its token response's `expiresIn` is the **API access token lifetime**. The currently reported response is numeric `"expiresIn": 7200`: 7,200 seconds, or 120 minutes. HID reads the value from each token response; it must not hardcode 7,200 seconds or change QoreID's returned expiry. HID's internal maximum-use window is 5,400 seconds (90 minutes), capped further if QoreID supplies a shorter lifetime: `effectiveTokenLifetime = min(expiresIn, 5400 seconds)`. The internal window is a cache/refresh policy, not a modification of the provider token.

The server must refresh or re-authenticate before using an internally stale token. A verification request that receives an unexpected QoreID `401` invalidates the cached token, obtains a new one, and retries that eligible request once; a second failure is returned safely without duplicate enrollment. Concurrent requests should share a refresh within the running server instance. Access tokens and credentials remain server-side, never appear in frontend responses, database rows, source control, or logs. Token behavior is verified with synthetic responses; the reported 7,200-second value has not been tested against a live QoreID token in this PR.

## Existing-patient NIN evidence

`POST /api/v1/identity/me/verification/nin` remains a separate governed route for a signed-in patient with an existing verified NIN binding. It uses canonical patient names and birth date for QoreID's documented name-matching request, and records evidence only. It cannot create or relink a patient. Migration `0050` removed the earlier unbound evidence command.

**The signed-in binding needs its own flag (ADR-062).** This route binds a NIN to a legacy patient on a name and date-of-birth match. It does not prove that the patient holds the NIN. While `QOREID_PATIENT_SELF_NIN_BINDING_ENABLED` is off (the default) it answers `503 QOREID_PATIENT_NIN_BINDING_DISABLED` ("Verifying a NIN from your account is not available", a fixed detail the problem filter keeps) before any lookup, quota charge or evidence row. Identity refuses the flag in production; whether decision N1 covers this route is the owner's decision. The admin integration view shows `existing_patient_nin` open only with this flag on.

## Organization application and CAC

`POST /api/v1/identity/organization-applications` accepts product, organization type, an `RC`/`BN`/`IT` registration identifier, and administrator contact. It does not accept an applicant-entered legal company name at intake. An admin with the exact review permission and expected row version invokes `POST /api/v1/admin/organization-applications/{id}/verify-cac`. The Identity API sends **only** `{ "regNumber": "<normalized prefixed identifier>" }` to QoreID CAC Basic V2 at `POST /v2/ng/identities/cac-basic`. Input whitespace and case are normalized; the `RC`, `BN`, or `IT` prefix is preserved.

**CAC provider verification** succeeds when the submitted identifier is valid, QoreID returns a numeric top-level `id`, `summary.cac_check="verified"`, `status.state="complete"`, and `status.status="verified"`. Missing or empty `cac.*` legal fields, or an omitted `cac` object, do not turn that verified lookup into a failed check. A present malformed `cac` object remains an invalid response. If QoreID returns `cac.rcNumber`, HID validates it against the submitted identifier: a digits-only number must match the submitted digits exactly, and an explicit prefix must also match. A mismatch fails verification. If `cac.rcNumber` is absent or empty, HID retains the normalized submitted `RC`/`BN`/`IT` identifier as the confirmed canonical registration identifier for the successful lookup; it does not invent a provider-returned number or require a second QoreID response. A populated non-active `cac.status` also remains provider-verified evidence, but it blocks review and cannot be replaced by the applicant.

**Organization profile completion** is a separate step. The adapter normalizes populated `cac.companyName`, `cac.companyType`, `cac.registrationDate`, `cac.address`, `cac.branchAddress`, `cac.companyEmail`, `cac.city`, `cac.headOfficeAddress`, `cac.lga`, `cac.affiliates`, `cac.state`, and `cac.status` into a server-only provider snapshot. The required review profile contains company name, entity type, registration date, address, and active registry status. HID stores each populated QoreID value as `qoreid` and keeps it authoritative. If QoreID omits a required field, the applicant may enter that field through the separate profile-completion flow; HID stores it as `user_provided`. The applicant cannot replace a populated QoreID field. Empty provider values remain absent, and no missing value is fabricated. `metadata.companyType` remains provider classification; it does not silently become `cac.companyType` or an applicant-confirmed entity type. The registration date becomes an ISO date, and HID prefers `cac.address`, then head-office address, then branch address for the required address. The additional returned city, email, branch address, affiliates, LGA, state, and metadata classification are normalized but have no separate persistence columns in the current schema.

The states remain distinct:

| Concept | Persisted/API state | Meaning |
| --- | --- | --- |
| CAC provider verified | `verification_result=verified`; verification API `state=verified`, `providerVerification=verified`; admin list `verificationResult=verified` | QoreID verified the submitted registration lookup and supplied a numeric reference. |
| Organization profile incomplete | `profile_state=incomplete` | A required review field is missing or QoreID reports a non-active registry status. The applicant may complete only fields QoreID omitted. |
| Organization profile complete | `profile_state=complete` | Every required field has a value with `qoreid` or `user_provided` provenance and registry status is active. |
| Ready for review | `status=ready_for_review` | Verified CAC and a complete sourced profile permit the existing governed admin review; no organization is active yet. |

A verified sparse lookup therefore records the provider reference, check time, canonical submitted registration identifier, and any returned fields, with `verification_result=verified`, `profile_state=incomplete`, and `status=pending_verification`. The applicant enters the same product, identifier, and administrator email at the completion route; HID sends a bounded, single-use email OTP to that application email. After OTP verification, a short-lived secure completion session can read the sourced profile and submit missing fields with an expected row version. Completing the required fields moves the application to `ready_for_review` without another QoreID call. This OTP proves control of the application email; it does not prove authority to represent the organization. A full provider profile can proceed directly to review with every required field sourced from QoreID.

Migration `0056_cac_applicant_profile_completion.sql` stores the provider snapshot separately from the merged review profile and records a source for every required field on the application and CAC binding. It converts historical `verified_incomplete` rows to verified provider checks with incomplete profiles, preserving their provider reference and canonical submitted identifier; migration `0055` did not retain their omitted or partial provider fields, so applicants must complete fields that cannot be recovered. Existing-organization evidence remains governed by migration `0054_complete_existing_cac_evidence_binding.sql`: a new lookup must satisfy the established binding before reuse. A unique registration binding, advisory lock, row version, and governed approval command protect against duplicate or concurrent organization creation. Only separate platform review activates the organization, product enrollment, and first administrator access. CAC Basic V2 does not verify beneficial ownership, directors, shareholders, an applicant's authority to represent the organization, or administrator identity.

Direct calls with the entitled QoreID sandbox account confirmed the verified sparse response shape for RC and BN identifiers: `cac.rcNumber`, `cac.companyName`, `cac.registrationDate`, `cac.companyType`, and `cac.status` were empty, while `cac.address` and `metadata.companyType` were present. IT remains supported by the request contract and synthetic tests; this sandbox observation did not test IT. Complete provider profiles and the full onboarding-to-activation path remain covered by synthetic tests and disposable database acceptance; separately reviewed staging acceptance remains open. No production verification is claimed. The raw QoreID response is not stored in audit logs or returned to the browser.

**Provider self-enrollment and a sparse record** (BRANCH:launch/provider-signup-answers). `POST /api/v1/identity/provider-enrollments` activates an organization without review, so it needs every required field from QoreID. When QoreID verifies the CAC but returns a sparse record (the shape above), or a complete record whose status is not active, start answers `409 PROVIDER_CAC_PROFILE_INCOMPLETE` with one detail that is true in both cases: "We could not register your organization automatically from its CAC record. The record is missing details we need or does not show the company as active. Contact Health ID support." It records nothing and sends no email code. The lookup is charged to the self-service CAC quota like any other lookup, so a retry repeats it within that quota. The applicant cannot enter the missing fields on this path. A verified answer that is malformed stays `502 QOREID_PROVIDER_RESPONSE_INVALID`. The governed application above can take a sparse record, but no launch page uses it (Health-id's public site is not deployed at launch), so the detail does not point to it. Before this change the sparse record answered `502`.

## Availability and secrets

`QOREID_ENABLED=false` and `QOREID_NIN_ONLY_ENROLLMENT_ENABLED=false` are the defaults. Identity refuses to start with `QOREID_NIN_ONLY_ENROLLMENT_ENABLED=true` in production (`HID_DEPLOYMENT_ENV=production`, or `NODE_ENV=production` outside the staging profile) until the NIN holder possession step of decision N1 ships (D-Eminence/hid-system#68). QoreID OAuth credentials remain server-only ECS Secrets Manager fields in the Identity task. When QoreID is paused in Admin Settings → Integrations, new NIN enrollment and other verification attempts fail closed; existing verified identities and Health IDs remain valid. CAC Basic V2 uses the general QoreID deployment gate and the enabled/paused integration state; both are default-off in the PR environment. No unapproved provider substitution occurs.
