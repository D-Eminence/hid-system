# Health ID frontend to HID backend capability matrix

Reference: `D-Eminence/Health-id` public web and product routes (inspected at `8903e68`), `D-Eminence/hid-1.0` for historical behavior, and this repository as the authoritative implementation. This matrix records readiness of the executable PR #5 tree.

| Future Health-id journey | Authoritative hid-system capability | State after this PR |
| --- | --- | --- |
| Patient signin, session, `/identity/me`, profile and self-service | Identity API patient authentication, secure cookie/bearer session, patient-scoped records and QoreID evidence | Existing; patient sign-in accepts email or the issued HIDCode, including phone-only accounts. Normal sign-in does not repeat NIN verification. |
| Get your Health ID / patient signup with NIN | `/patient/enroll` → NIN-only API → authoritative QoreID fixture with holder proof → encrypted pending identity → one HID contact OTP → password → atomic patient/account/HID activation | **Implemented and tested with fixtures; live provider activation pending.** Migration `0051` prevents duplicate NIN binding and activation before contact OTP and password. The NIN-only provider request, holder-proof contract, entitlement, credentials, and staging activation remain unconfirmed. The separate NIN-only gate is off by default, and the production adapter lacks a holder-proof mapper until the provider contract is approved. Existing-patient QoreID evidence remains a separate route. |
| EHR, Migrate, Laboratory, Pharmacy signup | Public `/provider/apply` form, Turnstile-protected identifier intake, admin CAC verification, registry identity binding, governed approval, product enrollment, first admin | **Implemented and tested with fixtures; live provider activation pending.** Migration `0052` requires exact identifier, name, entity type, date, address, and active status from QoreID; applicant company name is no longer authoritative. QoreID entitlement and prefixed/bare identifier mapping need provider confirmation. Platform review independently establishes applicant authority. |
| Existing organization adds a product | Complete CAC binding and explicit reuse review | **Implemented with fixtures; live provider activation pending.** The reuse command requires the complete bound legal entity and an existing active facility administrator. |
| Outreach campaigns, workspace members, status and field registration | Outreach API, canonical staff memberships, facility authorization, registration cases and events | Existing campaigns and field cases extended with optional campaign association and exact membership checks in `0045`. Existing facility-only cases remain valid. |
| EHR, Migrate, Laboratory, Pharmacy clinical workflows | Existing EHR, OCR/Migrate, Laboratory and Pharmacy services | Existing; no duplicate backend introduced here. |
| Public Book Demo and product-specific interest, including API | Identity API commercial demo intake and protected admin processing | Added by `0044`; API is an interest code, not self-service API credentials. |
| Public prices and protected admin editing | Single platform commercial catalog, product/context prices, immutable change events, optimistic versions and idempotency | Added by `0043`. Initially contact-sales with no invented monetary amounts. Changes become effective immediately; scheduled future pricing is not represented. |
| Admin signin and administration | Existing protected admin session and platform role model | Existing; there is no public admin signup. New demo, pricing and organization review routes require explicit platform permissions. |
| Admin Settings → Integrations | Identity-owned provider/capability catalog, runtime pause and compatible OTP routing, safe connection tests, secret-free audit history | Added locally in PR #5. Runtime controls apply only to supported providers; infrastructure integrations remain read only, and ECS-injected credentials still require external rotation and task rollout. See [provider integration management](PROVIDER_INTEGRATION_MANAGEMENT.md). |
| Separate Health-id site page structure, product copy, visuals and frontend calls | Frontend repository | The local hid-system patient enrollment and provider application are wired. The separate Health-id application remains an independent future frontend integration; its patient sign-in implementation is still a placeholder and cannot override the executable hid-system contract. Hardcoded public frontend prices must be replaced with the backend catalog there. |

Public NIN enrollment uses the submitted NIN as the stable duplicate key only after exact QoreID response binding and provider-backed holder proof; HID contact OTP proves control of the chosen phone or email, not ownership of the NIN. The published QoreID NIN-with-NIN endpoint requires applicant names, so the NIN-only request endpoint/entitlement and holder-proof contract must be confirmed before enabling the new path. CAC onboarding also needs the QoreID CAC Basic V2 entitlement and a confirmed mapping for prefixed `RC`/`BN`/`IT` numbers. See [the QoreID contract](QOREID_VERIFICATION_CONTRACT.md). The AWS CDK dependency audit remains a separate release gate while the official package still bundles vulnerable `brace-expansion`.
