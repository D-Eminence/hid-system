# Health ID frontend to HID backend capability matrix

Reference: `D-Eminence/Health-id` public web and product routes (inspected at `8903e68`), `D-Eminence/hid-1.0` for historical behavior, and this repository as the authoritative implementation. This matrix records readiness of the executable PR #5 tree.

| Future Health-id journey | Authoritative hid-system capability | State after this PR |
| --- | --- | --- |
| Patient signin, session, `/identity/me`, profile and self-service | Identity API patient authentication, secure cookie/bearer session, patient-scoped records and QoreID evidence | Existing; guarded by patient context and session checks. |
| Get your Health ID / patient signup with NIN | Governed NIN registration cases, duplicate checks, HID generation, enrollment, OTP credential setup | **Partial:** staff-led registration exists. QoreID's documented NIN response contains registry demographics and exact-match flags, but ordinary staging has no confirmed NIN entitlement or enabled credentials. The current API records evidence only for existing patients with an exact prior keyed NIN binding. An applicant-chosen email OTP does not prove control of the NIN identity. Public issuance awaits an approved possession or consent signal, stable duplicate key, and guarded enrollment flow. |
| EHR, Migrate, Laboratory, Pharmacy signup | Public `/provider/apply` form, Turnstile-protected organization intake, admin review, restricted CAC verification, canonical organization/facility, product enrollment, first admin | **Partial:** the frontend and governed backend are wired. Migration `0048` requires an active provider-confirmed legal name and exact registration-number binding before approval; reuse also requires exact legal-name reconciliation. QoreID CAC staging entitlement and the documented bare-number versus prefixed-number mapping still require provider confirmation. Platform review must independently establish applicant authority to administer the legal entity. No active organization can be created from a status-only result. |
| Existing organization adds a product | CAC binding and explicit reuse review | **Partial:** the reuse command requires a bound legal entity and an existing active facility administrator. Completion depends on the same QoreID CAC response and entitlement. |
| Outreach campaigns, workspace members, status and field registration | Outreach API, canonical staff memberships, facility authorization, registration cases and events | Existing campaigns and field cases extended with optional campaign association and exact membership checks in `0045`. Existing facility-only cases remain valid. |
| EHR, Migrate, Laboratory, Pharmacy clinical workflows | Existing EHR, OCR/Migrate, Laboratory and Pharmacy services | Existing; no duplicate backend introduced here. |
| Public Book Demo and product-specific interest, including API | Identity API commercial demo intake and protected admin processing | Added by `0044`; API is an interest code, not self-service API credentials. |
| Public prices and protected admin editing | Single platform commercial catalog, product/context prices, immutable change events, optimistic versions and idempotency | Added by `0043`. Initially contact-sales with no invented monetary amounts. Changes become effective immediately; scheduled future pricing is not represented. |
| Admin signin and administration | Existing protected admin session and platform role model | Existing; there is no public admin signup. New demo, pricing and organization review routes require explicit platform permissions. |
| Admin Settings → Integrations | Identity-owned provider/capability catalog, runtime pause and compatible OTP routing, safe connection tests, secret-free audit history | Added locally in PR #5. Runtime controls apply only to supported providers; infrastructure integrations remain read only, and ECS-injected credentials still require external rotation and task rollout. See [provider integration management](PROVIDER_INTEGRATION_MANAGEMENT.md). |
| Separate Health-id site page structure, product copy, visuals and frontend calls | Frontend repository | Later integration. The local hid-system public provider application page is wired; the separate Health-id frontend still needs its own integration. Hardcoded public frontend prices must be replaced with the backend catalog when that integration is undertaken. |

The main external dependency for patient self signup is an approved QoreID staging entitlement and a provider-confirmed possession or consent signal that establishes the applicant's control of a stable NIN identity for duplicate protection. Existing-patient evidence additionally requires the approved NIN lookup key in the staging Identity sensitive secret. CAC onboarding also needs the QoreID CAC Basic V2 entitlement and a confirmed mapping for prefixed `RC`/`BN`/`IT` numbers returned by the provider. `docs/QOREID_VERIFICATION_CONTRACT.md` limits the current patient route to evidence on an existing patient. The backend must preserve that limit. The AWS CDK dependency audit remains a separate release gate while the official package still bundles vulnerable `brace-expansion`.
