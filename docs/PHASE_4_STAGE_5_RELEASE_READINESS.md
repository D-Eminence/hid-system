# Phase 4 Stage 5: platform administration release readiness

This is the combined release checklist for the platform administration work
of Phase 4, the governed-access slice that followed it, the Stage 6 OCR
audit and queue-metrics slice, Stage 7 (MFA lock order and fail-closed OCR
validation guards), Stage 8 (fail-closed session guards and OCR worker
leases), Stage 9 (runtime command locking), the delegated cookie-read fix
(D-Eminence/hid-system#38), the sign-out and client-kind change
(D-Eminence/hid-system#39), the EHR clinical list paging fix
(D-Eminence/hid-system#40), the Outreach cookie-read fix
(D-Eminence/hid-system#43), the EHR to Lab order-time fix
(D-Eminence/hid-system#44), the patient PIN actor-window fix
(D-Eminence/hid-system#45, migration 0079), the EHR and OCR guard refusal
audit fix (D-Eminence/hid-system#46), the Pharmacy source prescription fix
(D-Eminence/hid-system#48, migration 0080), the Identity MFA key in the AWS
task definition (D-Eminence/hid-system#49) and the released Lab results change
(D-Eminence/hid-system#51). It covers Identity, the EHR, Lab,
Pharmacy, OCR and Outreach APIs, the OCR worker, the database and the AWS
regional stack in this repository, and in Health-id the admin console
(`apps/patient-web/src/admin`) and the provider
portal's governed-access pages
(`apps/patient-web/src/staff`). It records what was
verified locally and what an operator must still do. **Nothing here has been
deployed, and no staging or production database has been migrated.** Every
"verified" below means a local synthetic environment unless it says otherwise.

## 2. Stage 5 changes

- **Refresh-token revocation reason** (`token.service.ts`):
  - Only a rotated refresh token presented again is treated as reuse. Its family is revoked and `reuse_detected` is recorded, as before.
  - A token whose session ended any other way is refused. This covers sign-out, expiry, an administrator's revocation (revoke-all or a family revoke, including one marked compromised), a self-revocation, and an earlier reuse in the family. The refusal is recorded as a `refresh` session event with outcome `denied` and details `{ reason: 'session_ended', revocation_reason, session_kind }`. It is no longer recorded as reuse, and the family is not revoked again.
  - The same rule applies when a session ends while its refresh is in flight. A sign-out, expiry or revocation that commits first is reported as that end. Only a concurrent rotation of the same token counts as reuse.
  - Unchanged: a token whose account changed token version (suspension, platform MFA reset, password recovery, deletion) is not found by the refresh lookup at all. It is refused without a session event, as before. Platform tokens are answered `PLATFORM_SESSION_REVOKED`.
  - Answers are unchanged: platform `401 PLATFORM_SESSION_EXPIRED` (expired) or `PLATFORM_SESSION_REVOKED`, and generic `401 AUTHENTICATION_REQUIRED` for staff and patients. Only the problem `detail` changes, from "Refresh token reuse detected" to "Refresh session ended".
  - Before this fix, the console's normal refresh after an administrator revoked a session recorded `reuse_detected` twice per revocation. That made real token theft harder to spot.
- **CORS**:
  - Identity now allows `PATCH` (organization profile completion, `/identity/organization-applications/completion/profile`) and `DELETE` (patient access PIN, `/identity/me/access-pin`).
  - Pharmacy allows the `x-csrf-token` header that its cookie sessions send.
  - Origins, credentials and every other header are unchanged. No other service had a route whose method or header was missing. EHR's `PATCH` routes were already covered. Lab still lists `PATCH` without a route; that is left as is.
  - Same-origin `/api/v1` routing, the production design, never needed these. They matter only to a cross-origin deployment.
- **Session revocation serialization (Stage 5B, migration 0073)**: an administrator's family revocation (including one marked compromised), revoke-all, an administrator revoking one of their own sessions, and the family revocation after refresh-token reuse could each miss the session that a refresh in flight was creating. That session stayed live until it expired, even after a "compromised" revocation. Each of these revocations now takes the account row lock (`FOR UPDATE`) before revoking. The two admin commands lock the acting administrator's row with the target's, in account order: their idempotency row references the actor's account, so locking only the target would let two administrators revoking each other's sessions at the same moment deadlock. It waits for a refresh in flight to commit, then revokes the session that refresh created. A refresh that starts after the lock waits, then finds its session revoked and is refused. The admin commands `auth.admin_revoke_account_sessions` and `auth.admin_revoke_session_family` keep their signatures, permissions, checks, idempotency and results. The Identity API's own revocations call the new `auth.lock_account_sessions(uuid)`, which is granted to the Identity runtime only. These are refresh-token reuse, an administrator revoking their own session, sign-out and expiry. Sign-out and expiry end one session, but they take the lock first too. Every path that revokes sessions then locks the account row before any session row, so no two of them can deadlock. Without this, a sign-out during an administrator's revocation of the same account could deadlock. Account actions that change the token version (suspension, MFA reset, password recovery, deletion) already invalidated such a session and already locked the account first; they are unchanged. A sign-out now ends the whole sign-in, that is, the presented session's family. Before, a sign-out whose session another tab had just refreshed ended nothing, recorded a successful sign-out, and left the new session live.
- **Admin console (Health-id)**: after **Revoke all sessions**, the confirmation stays visible. Before, the reload reported no sessions and the form, with its confirmation, disappeared. This was found by the browser run in §8.
- **Governed access: the clinician's access-request list** (D-Eminence/hid-system#26, no migration). `GET /identity/access-requests` calls `identity.list_my_staff_access_requests(text)`, but the runtime grants never gave the Identity runtime `EXECUTE` on it. Every clinician's list was refused (`403`). The role bootstrap now grants it, and `runtime-roles.integration.sql` asserts the grant. `runtime-function-grants.spec.ts` checks, without a database, that every database function the Identity source calls is granted to its runtime.
- **Governed access: access-request outcomes** (D-Eminence/hid-system#28, migration 0074). An approved request stayed `approved` after its grant expired, was revoked by the patient or was closed by the clinician. The list now also returns, from the latest grant made from each request, `consentGrantId`, `grantExpiresAt`, `authorizationMethod` and `effectiveStatus`. For an approval with a grant, `effectiveStatus` reports whichever ended the grant first: `active`, `expired`, `closed` (by the requesting clinician) or `revoked` (by anyone else). Otherwise it is the request status. The `status` filter matches either the request status or the outcome, and also accepts `active` and `closed`. The function's arguments, caller checks, order and 100-row limit are unchanged.
- **OCR audit, queue metrics and outbox inserts (Stage 6, migration 0075)**:
  - **Read audit:** the OCR job lookup by document, the validation list and the publication list now write a patient-linked audit event (`ocr.job.find`, `ocr.validation.list`, `ocr.publication.list`) in the read transaction, after authorization; a failed audit write fails the read. Every OCR API job event, including the existing reads and writes, now names the source document's patient, which authorization resolves. Before, it used the job's own `patient_id`, which stays null for a job created without one, so those events were not linked to any patient. Details carry identifiers and counts only.
  - **Queue metrics:** the worker read `ocr.jobs` directly, which `hid_ocr_worker` may not do. Every read was refused, so `ocr.job.claimed` never carried `queueDepth` or `oldestQueueAgeSeconds`, and `OcrQueueAgeAlarm` and the QueueDepth signal had no data. The worker now calls `ocr.worker_queue_metrics()`, which returns only those two aggregates, with the same definitions. Its owner, the new non-login role `hid_ocr_queue_metrics`, reads only `ocr.jobs.status` and `queued_at` through one exact policy. The worker still has no table privileges.
  - **Outbox inserts:** `ocr.outbox_events` had only `SELECT` policies under `FORCE ROW LEVEL SECURITY`, so the OCR API runtime could not append outbox events. Patient confirmation and every publication request, success and failure failed with `new row violates row-level security policy`. 0075 adds a same-facility insert policy. The confirmation event is keyed by the job version, which a confirmation does not change, so a second confirmation of the same job version is now refused with `409 OCR_PATIENT_ALREADY_CONFIRMED`. Without that check it would fail on the outbox unique key with a `500`.
- **MFA lock order (Stage 7A, migration 0076)**: approving a platform MFA reset (`auth.admin_decide_approval`, 0070) locks the target's account row `FOR UPDATE`, then revokes its factors, recovery codes and sessions. Every MFA transaction of that account first locked its challenge and factor, or its session assurance and factor, or wrote a recovery code. It reached the account row only through the `FOR KEY SHARE` that its session event, session, recovery code or factor insert takes. The two could deadlock, and PostgreSQL then cancelled one. Reproduced locally for TOTP and recovery-code sign-in, step-up, recovery-code regeneration, enrolment activation and enrolment restart: each MFA request failed with `500` (§8). Every MFA transaction now calls the new `auth.lock_account_for_mfa(uuid)` (0076, granted to the Identity runtime only) before any other lock or write. That covers the password step, both sign-in methods, enrolment start and activation, step-up and regeneration. The order is then: the account; the challenge (sign-in and enrolment) or the session assurance (step-up); the factor and the recovery codes; then sessions and events. A challenge is found without a lock only to learn its account, then read again, locked, for that account. A request that waited for a reset is refused cleanly: `401 MFA_CHALLENGE_INVALID` for a sign-in or enrolment, `403 PLATFORM_SESSION_REQUIRED` for a step-up or regeneration. The helper takes `FOR NO KEY UPDATE`. It conflicts with the reset's and every revocation's `FOR UPDATE` and with itself, so MFA transactions of one account run one at a time, but not with the `FOR KEY SHARE` that refresh rotations and staff sign-ins take when they insert a session or a session event. Two other modes were rejected after the adversarial reviews, each reproduced locally (§8):
  - `FOR UPDATE`, the first version, which reused the revocation helper `auth.lock_account_sessions` (0073), made MFA transactions also wait for refresh rotations and staff sign-ins of the account. A step-up or regeneration that raced a refresh of its own sign-in waited, then found its session rotated and was refused `403 PLATFORM_SESSION_REQUIRED`, which ends the console session. The password step deadlocked with a staff sign-in of the same administrator through the principal's login-attempt row (`500`).
  - `FOR KEY SHARE`, the second version, does not conflict with itself, so MFA transactions of one account ran together. Each checked the second-factor failure limit before any of them had committed a failure: six parallel step-ups with a wrong code were all tested, where the limit allows five failures and then refuses (`429 MFA_RATE_LIMITED`), so one block window allowed about as many guesses as the Identity API has database connections. Two parallel password steps each left a challenge open, which also let an enrolment start overlap an activation. `main` before Stage 7 had no account lock and the same two gaps.

  With `FOR NO KEY UPDATE` none of these happens (§8). Platform session issue also resolves the administrator on the locked transaction's own connection, so the lock holder never needs a second pool connection (ADR-040).
- **Fail-closed OCR validation guards (Stage 7B, migration 0076)**: `ocr.validate_patient_confirmation` and `ocr.validate_validation_insert` compared with `<>`, which is NULL when either side is NULL, and a NULL condition did not raise. So a confirmation was accepted for any patient when the guard could not read the source document (missing, or hidden by row-level security from a non-bypass owner, P8), and a validation was accepted when the guard could not read the extraction or the session had no account or membership. Both now refuse a missing job, source patient, extraction, account or membership, and compare with `IS DISTINCT FROM`; the explicit `IS NULL` refusals are redundant in outcome only because every compared column of the new row is `NOT NULL`: `IS DISTINCT FROM` refuses a NULL against a value, but not a NULL against a NULL, which the `NOT NULL` constraint then refuses (`23502`, not the guard's `23514`). The confirmation guard also binds `confirmed_by` and `confirmed_by_membership_id` to the session, as the validation guard does for the reviewer; before, any session in the facility could attribute a confirmation to another member. Error codes and messages are unchanged, and the OCR API always writes the session's own account and membership, so its confirmations and validations pass as before. CREATE OR REPLACE keeps each function's owner and ACL; `SECURITY DEFINER`, `search_path` and volatility are restated exactly.
- **Fail-closed session guards and OCR worker leases (Stage 8, migration 0077)**. No service changes. Apart from lease renewal now succeeding, and a worker's failure of a job whose lease has expired now being refused (§3), the database refuses what it accepted before only for callers the services never are:
  - **OCR worker leases:** `ocr.complete_worker_job` and `ocr.fail_worker_job` compared the claim token with `<>`, so a NULL token passed the lease check: any session of the OCR worker subject, which every worker replica shares, could complete or fail a job another replica held. Both now refuse a NULL token (`55000`), as `ocr.renew_worker_claim` did, and `fail_worker_job` also refuses an expired lease. Missing result or failure metadata (content hash, payload, provenance, error code, retry flag, retry delay) is refused as invalid (`22023`); before, a NULL hash replayed a stored extraction and a NULL retry flag failed a job for good.
  - **OCR lease renewal:** the job trigger allowed no `processing` to `processing` update, so every `ocr.renew_worker_claim` was refused and the worker logged `ocr.job.lease_renewal_failed` every third of a lease. A job that ran longer than its lease (300 s by default) could not complete and was recovered and run again. Renewal now succeeds: an active lease may move later, at most an hour ahead, with the next version, and nothing else may change. A renewal records no status event.
  - **OCR job source evidence:** the job trigger compared the latest scan with `<>`, so a document with no scan event passed. An insert, a change of source, or the start of processing now needs an exact clean scan. Jobs created earlier without a scan event can still be failed, retried, renewed and validated; run P9 before the release to see whether any exist. The OCR API already refused such a source, and the worker never claimed one.
  - **Taking an OCR job out of play:** failing, cancelling or requeueing a job no longer re-reads its source evidence. Before, a job whose document was withdrawn (`entered_in_error`) or rescanned as not clean while it was processing could be neither completed nor failed, and the lease recovery in `ocr.claim_worker_job` then raised for every claim of its provider: OCR stopped for that provider until an operator repaired the data. Reproduced locally on 0076; a clinician marking a document entered in error during OCR was enough. Completing or validating such a job is still refused, and a requeued one is still claimed only with clean evidence.
  - **OCR publication requester:** a publication request may only name the session's own account and membership as requester (the attribution gap 0076 closed for confirmations).
  - **Lab, Pharmacy and Outreach guards:** the 13 guards that compared a row with the session's account or membership using `<>` (five Lab, five Pharmacy, three Outreach) refuse a missing session account, membership or facility, and Outreach a purpose other than direct care, with their existing codes and messages. Forced row-level security already refused such writes for the runtime roles; a session that bypasses it (a superuser, or an owner without `FORCE ROW LEVEL SECURITY`) could write rows attributed to any member with no context. The Lab OCR-import guard also refuses another facility's OCR evidence when its owner cannot read it (P8).
  - **Outreach runtime grant:** Outreach policies call `platform.current_account_id()` as the runtime, which calls `auth.account_id_for_subject(text)`, revoked from PUBLIC. The Outreach runtime had no `EXECUTE` on it, so every Outreach write failed with `42501` since the baseline. The bootstrap now grants it; `runtime-roles.integration.sql` and the Outreach API spec `runtime-function-grants.spec.ts` check it. Campaign-linked registration still failed on a separate defect, fixed in Stage 9 (§4.2).
- **Runtime command locking (Stage 9, migration 0078)**. The locking statements of §4.2 failed for the runtime roles. Each path now locks only a row its runtime role may update, or none; no table gets a new `UPDATE` grant or policy (ADR-042):
  - **Pharmacy** (`pharmacy.service.ts`): the six locks are gone. They locked work items, dispensings, reversals and imported evidence, which the Pharmacy runtime only inserts; append-only triggers refuse every update and delete. Unique constraints decide concurrent writes (one work item per prescription and per key, one dispensing per work item, one reversal per dispensing, one import per publication, one row per key), with the session guards and `SERIALIZABLE`.
  - **Lab** (`lab-imports`, `lab-work-items`, `lab-accessions`): the import replay, EHR-order acceptance and accession reads no longer lock. Imported evidence, work items and accessions are insert-only; append-only triggers refuse their updates, and unique keys allow one import per publication, one work item per EHR order, one accession per work item, and one row per key. The remaining Lab locks (specimen, execution, result) are on rows the Lab runtime updates.
  - **OCR** (`ocr.service.ts`): the validation and confirmation replays no longer lock the insert-only validation and confirmation, and a publication request no longer locks its validation. The job row, which the OCR runtime updates, stays the lock taken first by retry, validation, confirmation and publication requests; the database guards also lock it as their owner and require the next version. A publication replay reads its publication without a lock, and the publish and failure transactions of a publication take the job's key share, which their outbox insert's foreign key takes anyway, before the publication row. Stage 9 made publication requests reachable, and with them a deadlock between a request holding the job and a publish transaction holding the publication (§8). Because the replay read takes no lock, a resent request that waited for the job while the owning domain rejected the first one read the publication from before the rejection and sent it to the owning domain again; the claim now refuses a terminal failure itself, by the same rule as the request, and answers `409 OCR_PUBLICATION_TERMINAL` (found by the independent review, race-tested, §8).
  - **Outreach** (`outreach.service.ts`): a campaign-linked registration locks the campaign alone (`FOR SHARE OF campaign`), not the membership row, so a campaign close still waits for registrations in flight or makes them fail and retry. The campaign lock applies the campaign `UPDATE` policy, so every role with `outreach.registration.write` must also hold `outreach.campaign.write`; all shipped roles do, and `runtime-command-privileges.integration.sql` checks it.
  - **Identity** (`nin-registration.service.ts`): `loadCaseForUpdate` locks the registration case alone, then reads the case with its patient in a second statement. The read sees a review that committed while this one waited, and the review then answers its replay or a conflict.
  - **Transaction retry:** the Pharmacy, Lab, OCR and Outreach `DatabaseService` run a `SERIALIZABLE` transaction again, up to twelve attempts in all, when PostgreSQL cancels it with `40001` or `40P01`, as the PostgreSQL manual recommends, or a unique violation `23505`, which the manual says may be worth retrying but can be persistent, after a random pause within a window that doubles from 20 ms up to 1 s. A unique violation (`23505`) is retried once: it means the conflicting row has committed, so the next attempt sees it and replays it, and a second one is a real conflict. Services map a remaining conflict to `409` only after the retry, except two real conflicts a retry cannot resolve, which are mapped inside the transaction: the OCR confirmation outbox key (`409 OCR_PATIENT_ALREADY_CONFIRMED`) and an existing Outreach campaign member (`409 OUTREACH_CAMPAIGN_MEMBER_EXISTS`); Outreach registration used to map it inside the transaction, so the loser of two identical requests could get `409 OUTREACH_REGISTRATION_CONFLICT` instead of the replay (seen once in the rehearsal). The retry sees the committed winner of a race and replays it or refuses the request (`409`, `412`), where it used to answer `500`. Other isolation levels and other errors run once. PostgreSQL tracks `SERIALIZABLE` reads by index page, so on small tables concurrent requests for different rows also cancel each other, and of a group that overlapped only one commits: eight concurrent dispenses of different work items, each with a 20–40 ms Identity call inside its transaction, failed with `500` under a retry of three attempts 5–15 ms apart. The budget was measured (§8): with eight attempts, 2 of 640 such writes, 16 at once, still failed; with ten or twelve, none of 3,200 failed and none needed more than 9 attempts.
  - **Two defects behind the locks (0078),** hidden because each command failed at its lock first:
    - The `patient_identifiers_self_nin_insert` policy (0058) applies to every role and read `identity.verification_evidence`, which the Identity runtime cannot read. PostgreSQL checks the privileges of every applicable policy, so every Identity runtime insert of a patient identifier failed with `42501`, including both NIN registration reviews. 0078 drops that policy rather than repair it. The only writer of self-NIN identifiers is `identity.bind_my_verified_nin`, a definer owned by the table owner, and `identity.patient_identifiers` does not force row-level security, so the function never used the policy; the policy only let another role insert a self-NIN identifier directly, without the binding function's checks (the patient's own session, crosswalk ownership, manual review, single-NIN eligibility, the per-NIN lock). Repairing its privileges would have given that to the Identity runtime (found by the Stage 9 review; reproduced). The registration review's own insert policy is unchanged.
    - `lab.validate_work_item_child` (0018) read `NEW.ordinal` on `lab.work_item_events`, which has no such column (`42703`), so every Lab acceptance of an EHR order failed at its acceptance event. 0078 reaches the requested-test check only for `lab.work_item_requested_tests`; the checks are unchanged.
  - **Checks:** `scripts/verify-runtime-locking-privileges.mjs` (`npm run verify`) compares every lock clause in the service source with the privileges, policies and row-level security its runtime role has after replaying the migrations and runtime grants, and refuses the locks PostgreSQL refuses for every role (the nullable side of an outer join, `DISTINCT`, `GROUP BY`, aggregates, window functions, set operations). Lock text it cannot place in a statement it can assemble fails the check; SQL assembled by string operations outside literals (a keyword split across a concatenation, a `.replace()` on a statement) is left to the runtime command suite and the verifiers. The rehearsal also compares that replay with the migrated catalogue. On `main` it reports the 14 failing clauses of §4.2; now none. CI runs it in the workspace gates job (`tuf-local-gates.yml`, `release/scripts/run-workspace-gates.mjs`), with its tests and the rehearsal.
- **Delegated cookie reads (D-Eminence/hid-system#38, no migration)**. EHR, Lab, OCR and Pharmacy authorize each patient-scoped request through `POST /identity/service/authorization/check`, forwarding the browser's cookie. Identity's `SecurityGuard` treated that POST as a browser write and required `Origin` and `X-CSRF-Token`, which a same-origin browser `GET` does not send, so every delegated read from a cookie session was refused `403 ORIGIN_DENIED`. Reproduced locally over HTTP for a doctor's cookie-only `GET /ehr/patients/:id/encounters`; Lab, OCR and Pharmacy reads take the same path.
  - **Services:** each `requireRequestContext` now records `request.method` as `requestMethod`, and `@hid/api-client` sends it to Identity as `X-HID-Original-Method` (upper-cased, only when it is 1–16 letters). Only the patient authorization call passes it.
  - **Identity:** the new `@DelegatedBrowserRequest()` (`common/decorators.ts`) marks `service/authorization/check` only. On that route `SecurityGuard.delegatedSafeBrowserRequest` skips the cookie Origin and CSRF check when the reported method is exactly `GET`, `HEAD` or `OPTIONS` and the request authenticates through `WorkloadAuthService.authenticateService` as any approved caller (`ehr-api`, `lab-api`, `pharmacy-api`, `ocr-api`, `outreach-api`). Identity cannot check the reported method itself; it relies on the authenticated workload (§9; ADR-043).
  - **Unchanged:** a reported write, a missing, lower-case or unknown method, a wrong or missing workload token and an unapproved caller name all keep the check (`ORIGIN_DENIED`, or `CSRF_VALIDATION_FAILED` with an allowed Origin and no CSRF). Every other route keeps it, including `POST /auth/service-session`, through which the four services still revalidate a real cookie write's Origin and CSRF before acting. Bearer transport, facility, permission, workload authentication in the handler and the patient decision are unchanged. Outreach's own Identity routes (`POST /identity/outreach/authorize` and `POST /identity/outreach/patient-authorization`) are not marked (the Outreach cookie-read branch below marks the first). Its one patient authorization call, for the link-existing write (`IdentityService.authorizeExistingPatient`), goes to the marked route but sends no method, so the check still applies.
- **EHR clinical list paging (D-Eminence/hid-system#40, no migration)**. The six newest-first clinical lists (`GET /ehr/patients/:id/encounters`, and an encounter's `clinical-notes`, `diagnoses`, `lab-requests`, `prescriptions` and `vitals`) page with a keyset cursor on (sort key, `id`). The keys are `timestamptz` columns with microseconds: `created_at` defaults to `clock_timestamp()`, and `started_at` and `recorded_at` keep any fraction the client sends. The cursor was built from the row's JavaScript `Date`, which node-postgres gives only milliseconds, so the next page's bound fell to the start of the last row's millisecond. Rows that sort after the last row shown within its millisecond (earlier in that millisecond, or tied with a lower `id`) were never listed, most likely rows created in bulk or by import (Health-id `docs/OPEN-QUESTIONS.md`, "Timeline pages skip rows within a millisecond").
  - Each list now also selects its key as microsecond text (`to_char(key at time zone 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US"Z"')`), and the cursor carries that text, never the `Date`. The text has a five- or six-digit year after 9999, which `started_at` and `recorded_at` can hold because they take any instant the client sends; the cursor accepts those years, up to 294276, the last a `timestamptz` holds.
  - The cursor is now version 1, bound to its list, its patient and, for the five encounter lists, its encounter, and accepted only in the exact form issued, as Identity's admin cursors are. A well-formed cursor (16–512 base64url characters) in any other form, including every cursor in the earlier millisecond format, is `400 INVALID_CURSOR`. A `cursor` that is not well formed is still `400 VALIDATION_FAILED`.
  - The response shape `{ items, nextCursor }`, `limit` (1–100, default 50) and the queries' predicates, order and parameters are unchanged (`INTERFACE_CONTRACT.md` §11, `DATABASE.md`).
- **EHR to Lab order time (D-Eminence/hid-system#44, no migration)**. Lab accepts an EHR order only when the work item's `requested_at` equals the order's `created_at` exactly (`lab.validate_work_item`, 0077). `created_at` defaults to `clock_timestamp()` and keeps microseconds, but EHR sent `requestedAt` from the row's JavaScript `Date`, which node-postgres gives only milliseconds, so once Stage 9 had removed the earlier failures Lab still refused almost every order (SQLSTATE `23514`, `500`). EHR now selects `created_at` as microsecond text (`timelineCursorSql`, as the paging fix does) when it creates the order and on an idempotent replay, sends that text as `requestedAt`, and keeps it out of its response (`INTERFACE_CONTRACT.md`, Extracted Lab transport).

  - D-Eminence/Health-id#18 reads the list above, closes a grant, and enables clinical writes only when `POST /identity/consent-status` allows them.

- **Sign-out by refresh cookie, and refresh and sign-out of the calling app's sign-in only** (D-Eminence/hid-system#39; Identity only, no migration or grant change). The contract is in `INTERFACE_CONTRACT.md` ("Auth session contract") and the decision in ADR-044.
  - **Idle sign-out:** `POST /auth/logout` needed a live access token. The access cookie lasts 15 minutes and the refresh cookie 8 hours (defaults), so a browser left idle could not sign out: the guard answered `401` before the handler ran, the cookies were not cleared, and the sign-in stayed refreshable until its refresh window ended. Sign-out now authenticates itself. A live access token ends its own sign-in, as a bearer token or as the cookie with an allowed `Origin` and its CSRF token. Without one, the refresh cookie ends its sign-in when the request carries the CSRF token derived from that refresh token. A live access token always decides, so another account's refresh cookie riding along is never ended. A cookie sign-out without an allowed `Origin` is `403 ORIGIN_DENIED` and changes nothing; every other outcome except `SESSION_CLIENT_MISMATCH` clears the cookies. Platform maintenance and a disabled portal no longer block sign-out.
  - **Client kind:** the staff and patient portals share the session cookies on one origin, so a stale tab of one could rotate the other's sign-in by refreshing, or end it by signing out. `POST /auth/refresh` and a cookie `POST /auth/logout` read `X-HID-Client` (`staff-web` or `patient-web`). After the Origin and CSRF checks, a sign-in of the other kind that refresh could renew now is refused with `403 SESSION_CLIENT_MISMATCH`: nothing is rotated or ended and the cookies are kept (below for any other). A bearer sign-out ignores the header, and an app that does not name itself behaves as before. Identity's CORS allow-list now admits `x-hid-client`.
  - **Lookups:** the kind is answered only for a sign-in refresh could renew now: the account is active, not disabled and on its token version, the absolute end has not passed, and the token's session is live or was rotated within the last 60 seconds into one that is. On refresh, any other token goes on to rotation; an older rotated token is reuse, which ends the sign-in. Sign-out by refresh cookie reads the sign-in under the account lock and ends whatever is left of it (the session unrevoked, or rotated into one that is), whatever its expiry or the account's state, so a sign-out during a timed suspension leaves nothing to renew when it lapses. A sign-in it may not name is ended whichever app asks, without naming its kind, so an old rotated token tells nobody whether, or as which app, its sign-in is live. Every sign-out ends only sessions still unrevoked under the account lock, and records and audits only when it ended one, so a replayed cookie or two tabs signing out at once, by either path, record one sign-out.
- **Refusals on session routes audited as session events** (Identity only, no migration or grant change). The global `AuditInterceptor` recorded a refused request as a generic `api.*` HTTP request. On a session route (sign-out, facility selection, the session and service-session reads, Google link) usually no facility is bound (never on sign-out; on the others only with `X-Facility-ID`), and a staff audit row without a facility is accepted only as an `auth.*` session event (`AuditService.assertActorFacility`, and 0067's `events_staff_facility_scope_check` and `events_staff_membership_scope_check`). So a staff refusal there failed its own audit and answered `503 DEPENDENCY_UNAVAILABLE` instead of its refusal, unrecorded:
  - a cookie sign-out with a live staff access cookie refused for `SESSION_CLIENT_MISMATCH` or `CSRF_VALIDATION_FAILED`;
  - `POST /auth/facility` for a facility without membership (`403 FACILITY_ACCESS_DENIED`) or with a malformed id (`400`).
  These routes now carry `@AuditSessionEvent('auth.*')`, and the interceptor records them as that event on resource type `session` and the actor's session, with the actor's kind and no facility, membership or organization unless the guard bound one from `X-Facility-ID` (never on sign-out). No facility rule is relaxed. Patient refusals, and anonymous refusals of sign-out, raised after the `SecurityGuard` keep their answers; their rows are now `auth.*` session events instead of `api.*` HTTP requests (§3). The guard's own refusals never reach the interceptor and keep their rows.
- **Outreach cookie reads (D-Eminence/hid-system#43; no migration or grant change)**. Outreach authorizes every request through `POST /identity/outreach/authorize`, forwarding the browser's cookie. Reproduced locally over HTTP in the migration rehearsal on `main` (`522fb2e`), with Outreach as `hid_outreach_api_runtime` and Identity as `hid_identity_api_runtime`, same-origin cookie reads were refused at three layers in turn. Outreach's guard (`outreach-security.guard.ts`) required an allowed `Origin` and an `X-CSRF-Token` on every cookie request, `GET` included, so every cookie read (`GET /outreach/registration-cases`, `/:caseId`, `/campaigns` and `/campaigns/:campaignId/members`) was refused `403 CSRF_VALIDATION_FAILED` (the #38 known limit, §9). With only that fixed, Identity refused the forwarded cookie on the authorize call with `403 ORIGIN_DENIED`: the route was not marked and Outreach reported no method. With both fixed, every campaign route answered `400 VALIDATION_FAILED`, because Identity's `AuthorizeOutreachDto` accepted only `outreach.registration.read` and `outreach.registration.write`. The decision is ADR-045.
  - **Outreach:** the guard treats `GET` and `HEAD` as reads. A cookie read needs no `Origin` or CSRF token; one that names a disallowed `Origin` is `403 ORIGIN_DENIED` (in production Outreach's CORS layer refuses a disallowed Origin even earlier). A cookie write keeps the presence check: an allowed `Origin` and an `X-CSRF-Token`, else `403 CSRF_VALIDATION_FAILED`. A read route mapped to a permission that is not a `.read` fails closed with `500 OUTREACH_POLICY_INVALID`. The guard passes `request.method` to the typed Identity client as `requestMethod`, which reports it as `X-HID-Original-Method` on the authorize call.
  - **Identity:** `POST /identity/outreach/authorize` is marked `@DelegatedBrowserRequest()`, under #38's conditions. When `SecurityGuard` skips the cookie-write check for a read reported by an authenticated workload, it records the method in `request.delegatedBrowserMethod`. `authorizeOutreach` still requires the `outreach-api` workload (`authenticateOutreach`), and after such a skip authorizes only a permission ending in `.read` (`403 CSRF_VALIDATION_FAILED` for a write permission). `AuthorizeOutreachDto` accepts exactly `OUTREACH_PERMISSIONS`, three of the four permissions that migrations 0024 and 0038 define: `outreach.registration.read`, `outreach.registration.write` and `outreach.campaign.read`. It still refuses `outreach.campaign.write` with `400 VALIDATION_FAILED`, as on `main`, and Outreach relays that status and code.
  - **Campaign writes (open product decision):** an earlier version of the branch also accepted `outreach.campaign.write`; that is withdrawn after a security review. The campaign write routes have no campaign-level governance: `OutreachService.addCampaignMember` (`outreach.service.ts:226-234`) checks only that the campaign belongs to the facility and inserts the caller-supplied membership and role, `admin` included; the insert policy `outreach_campaign_members_create` (`0038_outreach_campaign_workspaces.sql:99-104`) requires only `outreach.campaign.write` at the facility and `added_by` equal to the caller; `updateCampaignStatus` has no member or role check; and the restrictive policies of 0045 gate a campaign's linked registration cases only on a `campaign_members` row existing. With the permission authorized, any holder of `outreach.campaign.write` at the facility (doctor, clinician, nurse, receptionist, admin and org_admin, 0038) could add themselves to any campaign as `admin`, read its linked registration cases (name, phone, sex, age, notes), and close or activate any campaign. A second review found that this is 0038's design rather than a defect in it (facility-level campaign managers: `0038_outreach_campaign_workspaces.sql:6`, `schema.integration.sql:2096-2130`, `0045_outreach_campaign_registration_binding.sql:116-118`), that the DTO's two-permission limit was an oversight predating the campaign routes (`a8b3889`), and that, while `outreach.campaign.write` stays refused, no campaign and so no campaign-linked case can be created through the API (since D-Eminence/hid-system#34 a campaign member can record one, once a campaign exists). The campaign-linked registration compartment (0045) is only as strong as who may add campaign members. Who may create campaigns, change their status and add members is therefore a product decision, which this branch does not take: option A authorizes `outreach.campaign.write` as 0038 designs it (a one-line DTO change); option B adds per-campaign governance first, for example only the campaign's own `admin` members, in `OutreachService` and in RLS by a new migration, with failing-first SQL and HTTP tests (ADR-045). Until then the campaign create, status change and member add answer `400 VALIDATION_FAILED` even with an allowed `Origin` and the session's CSRF token, as on `main`, and change nothing, so no campaign can be created through the API. Campaign reads are authorized. Registration-case routes are unchanged by this narrowing.
  - **Unchanged:** `POST /identity/outreach/patient-authorization` is not marked, and the link-existing patient authorization still reaches `service/authorization/check` without a method, so the check applies there. Bearer requests are checked as before. Outreach cookie writes still need `Origin` and CSRF, and Identity still verifies the CSRF token against the session on the authorize call. Campaign-linked registration as the runtime role works since D-Eminence/hid-system#34 (§4.2), for a campaign that exists; none can be created through the API while campaign writes stay refused. Health-id needs no change for the reads: it already sends cookies with credentials and `X-CSRF-Token` only on writes. Its Outreach page can list campaigns and members, but its campaign create, status and member actions get `400 VALIDATION_FAILED`, as on `main`; until the campaign decision, Health-id should hide or handle them.
- **Patient PIN actor window (D-Eminence/hid-system#45, migration 0079; no service or grant change)**. `identity.access_patient_with_pin` (0033) cleared the clinician's actor failure window on every correct PIN, for any patient, so a clinician who knew one patient's PIN could guess another's four times, enter the known PIN, and repeat without ever reaching the five-failure actor lock. 0079 replaces the function (`CREATE OR REPLACE`; signature, result, `SECURITY DEFINER`, `search_path`, owner and grants unchanged) so a correct PIN clears only the failure window of the patient it verified (`DATABASE.md`, "Patient access PIN actor window (0079)").
  - **Behaviour change:** a clinician who mistypes PINs for several patients within 15 minutes can now reach the 15-minute actor lock even if some PINs were right in between. Support should expect this; the lock lapses on its own (§5 step 12).
- **EHR and OCR guard refusals before a facility is bound** (D-Eminence/hid-system#46; no migration or grant change; `auth/remote-security.guard.ts` in `services/ehr-api` and `services/ocr-api`). `RemoteSecurityGuard` audits each refusal before answering it. When it refused a staff request before binding a facility (`400 FACILITY_REQUIRED` for a missing or malformed `X-Facility-ID`, `403 FACILITY_ACCESS_DENIED` for a facility the actor is no longer active at, such as a stale tab, and in EHR the runtime controls `423 PLATFORM_PORTAL_DISABLED`, `503 PLATFORM_MAINTENANCE` and `503 PLATFORM_CONTROL_UNAVAILABLE`), it wrote a `security.authorization.denied` row on `http-request` that carried the membership and organization of the actor's default facility but no facility. `AuditService.assertActorFacility` and 0067's `events_staff_facility_scope_check` and `events_staff_membership_scope_check` accept a staff row without a facility only as an `auth.*` event on `authentication` or `session`. So the write failed closed, the client got `503 DEPENDENCY_UNAVAILABLE`, and nothing was audited. OCR recorded every actor as `staff`, so a patient refused by OCR got the same `503`.
  - A refusal with an actor and no bound facility is now recorded the way Identity's `SecurityGuard` records it: `auth.authorization.denied` on `authentication`, `actorType` `staff` or `patient`, the subject and account, and no facility, membership or organization. The request gets its own status and code back.
  - **Runtime-control faults (EHR):** `controlEnabled` rethrew every database error other than `55000`, and the guard answers an error that is not a refusal as `401 AUTHENTICATION_REQUIRED`. A staff request still got `503 DEPENDENCY_UNAVAILABLE` only because its audit row failed; with the audit fix alone it would have got `401`, and a patient always did. A statement timeout, a lost connection or a missing grant on `platform.control_enabled` now answers `503 PLATFORM_CONTROL_UNAVAILABLE`, the code a `55000` other than the disabled marker already had, and is recorded like the other refusals before a facility is bound. OCR's guard reads no runtime control.
  - Unchanged: a refusal after a facility is bound (`403 PERMISSION_DENIED`) keeps its `security.authorization.denied` row on `http-request`, with that facility, membership and organization. An unauthenticated request keeps its `system` row. The audit service, the CHECKs and every authorization check are untouched. OCR's `ActorContext` gains the optional `kind` that Identity already sends, and both OCR audit branches read it as EHR's do. A patient never reaches OCR's facility-bound branch (no OCR route is facility-optional), so that branch records as before.
- **Pharmacy work bound to its EHR prescription (D-Eminence/hid-system#48, migration 0080; EHR and Pharmacy APIs; no grant change)**. Pharmacy never read the EHR prescription: it accepted a snapshot of a prescription that was cancelled, superseded or did not exist (the EHR checks eligibility in its own transaction, which commits before it calls Pharmacy), and it dispensed a work item after the prescriber had cancelled, marked entered in error, put on hold, completed or edited the prescription. Health-id offers all of these EHR actions and keeps showing the dispense form for such work (`DATABASE.md`, "Pharmacy source prescription guards (0080)"; `INTERFACE_CONTRACT.md` §13; ADR-042 addendum).
  - **Database:** 0080 replaces `pharmacy.validate_work_item()` and `pharmacy.validate_dispensing()` (`CREATE OR REPLACE`; signature, `SECURITY DEFINER`, `search_path`, volatility, owner and the 0077 checks unchanged). After the 0077 checks each reads the prescription as its owner with `SELECT ... FOR SHARE`. An acceptance must equal the exact active prescription version, field by field except the prescription time and the start and end dates (below); a dispensing needs its prescription still `active` at the accepted version. Each refusal is `23514` naming its constraint (`pharmacy_work_item_source_prescription`, `pharmacy_dispensing_source_prescription`). Reversal is unchanged.
  - **Pharmacy API:** those two refusals answer `409 PHARMACY_PRESCRIPTION_NOT_ELIGIBLE` (acceptance) and `409 PHARMACY_PRESCRIPTION_NOT_DISPENSABLE` (dispensing), with nothing written; EHR passes the acceptance code through on its handoff command. Every other check violation answers as before (`500`). Replays are answered before the check: an identical earlier acceptance or dispensing is still returned with `201` after a cancel.
  - **EHR API:** the handoff reads `created_at` as microsecond text and `starts_on`/`ends_on` as `YYYY-MM-DD` in its locking query and sends those texts, instead of node-postgres `Date` values (milliseconds; a date at local midnight, a day early in a process east of UTC). 0080 does not compare them yet (below); the eligibility transaction still commits before the call, so no lock is held across HTTP.
  - **Prescription time and dates not compared yet:** the acceptance guard does not compare `prescribed_at` with `created_at`, or `starts_on` and `ends_on` with the prescription's dates; Pharmacy stores them as sent, as before 0080. Migrations run before the EHR API is deployed (§6) and the EHR API may be rolled back (§9). Every earlier EHR build sends `created_at` truncated to the millisecond, and the dates as local-midnight `Date` values, a day early in a process east of UTC, so an exact time term in this release would refuse nearly every acceptance those builds send, and exact date terms every dated one sent from a process east of UTC. Follow-up for a later release: add the three terms in a new migration once the EHR rollback floor includes this change.
  - **Races:** the Pharmacy commands are `SERIALIZABLE`. A cancel in progress is waited for; one that commits after the command's snapshot fails the share lock with `40001`, and the retry reads it and refuses. An EHR update waits for a dispensing or acceptance that holds the share lock, milliseconds, and applies after it.
  - **Open product question (current default):** the guard requires the accepted version, not only an active status. So a hold then resume, or any edit (frequency, instructions, end date), also makes the work item undispensable, it stays listed as `accepted`, and the prescription cannot be accepted again (one work item per prescription): the remedy is a new EHR prescription and handoff. A cancel after a dispensing does not undo it and is reported to no one. What should happen to accepted work when the EHR changes the prescription, and whether a later cancel of a dispensed prescription should be surfaced, is for product to decide.
- **Identity MFA key in the task definition** (D-Eminence/hid-system#49; `infra/aws` only, no migration, grant or service change). Identity reads `MFA_SECRET_KEY_B64` and `MFA_KEY_VERSION` (Stage 2A), but no task definition supplied them, so in every AWS environment platform sign-in failed closed with `503 MFA_UNAVAILABLE` and the version defaulted to `local-v1` (P3).

  - `infrastructure.test.ts` asserts this for production, development and every staging mode, QoreID included; `verify-synth.mjs` asserts it on each synthesized profile. Both also require the description to name every field the task reads from the secret (the unit test: exactly those fields, in every profile including QoreID staging).

Presence alone passed a hex or unpadded key that then stops every Identity task at start-up. The receipt stays value-free.

- **Released Lab results for clinicians** (D-Eminence/hid-system#51; Lab API only, no migration or grant change). The contract is in `INTERFACE_CONTRACT.md` ("Lab execution and governed-result API").
  - **Unreleased values:** `GET /lab/results/:resultId/history` (`lab.result.released.read`) refused only a result with no released revision. - Campaign-linked Outreach registration now requires `outreach.campaign.write` as well as `outreach.registration.write` (the campaign lock applies the campaign `UPDATE` policy). Every shipped role holds both. A custom role with only the registration permission gets `403 OUTREACH_CAMPAIGN_ACCESS_DENIED` for a campaign-linked registration.
- Lab orders created on the EHR while Lab acceptance was failing have no Lab work item (§10).

**Pharmacy source prescription (D-Eminence/hid-system#48, 0080):**
- The EHR API keeps its place in §6 and may be rolled back: 0080 does not compare the prescription time or dates, so earlier EHR builds, which send the time at the millisecond, keep handing off. An earlier EHR build in a process east of UTC sends start and end dates a day early, which Pharmacy stores as it did before 0080; no service image or deployment sets `TZ`, so the processes run in UTC. The new EHR build works on 0079 and with earlier Pharmacy builds, which accept the exact texts (and store `prescribed_at` at the microsecond instead of the millisecond).
- Deploy the Pharmacy API with the `409` mapping before or with 0080. An earlier Pharmacy API on 0080 answers the same refusals with `500`; nothing is written either way. The new Pharmacy API on 0079 never meets these refusals.
- Pharmacy's idempotency digest covers the request text, so an acceptance sent by an earlier EHR build and sent again after the EHR upgrade, with the same key or for the same prescription, gets `409 IDEMPOTENCY_CONFLICT` (the EHR passes it through); Pharmacy still has its work item. The reverse holds during a rolling EHR deploy or after an EHR rollback.
- When 0080 is applied, existing accepted work items without a dispensing whose prescription changed after acceptance (cancelled, entered in error, on hold, completed, or edited to a later version) become undispensable at once and answer `409 PHARMACY_PRESCRIPTION_NOT_DISPENSABLE`; this includes staging S4g items (§10 lists them). Work items accepted from an earlier EHR build keep dispensing: neither guard compares the prescription time or dates.
- Pharmacy can now delay an EHR write: a dispense or acceptance holds `FOR SHARE` on the prescription until it commits. A Pharmacy transaction that stalls after the guard (Pharmacy's 15 s `statement_timeout` bounds a statement, not an idle transaction) makes a prescriber's cancel or hold of that prescription wait until the EHR's 15 s `statement_timeout`, and the EHR command then fails with `500`.
- Health-id needs no change: its dispense form shows the problem detail of a `409`. It still shows the dispense form for work that can no longer be dispensed.

- Same-origin cookie reads through a service work only once both that service and Identity run #38. Either side alone behaves exactly as before: an earlier Identity ignores `X-HID-Original-Method`, and an earlier service does not send it, so the read is still refused `403 ORIGIN_DENIED`. OCR's cookie reads (a job, find-by-document, extractions, validations and publications) also need EHR with #38, because OCR reads each job's source document through EHR's `GET /ehr/internal/ocr/documents/:id/source`, which EHR authorizes with the forwarded cookie. Deploy in any order; OCR reads work once OCR, EHR and Identity all run #38.
- Writes, bearer requests and Outreach behave the same with any combination of builds.

**EHR clinical list paging:**

- The new EHR build refuses every cursor an earlier build issued, and an earlier build refuses the new cursors, both with `400 INVALID_CURSOR`. A browser that holds a cursor across the deploy, or meets both builds during a rolling deploy, gets that refusal on its next paged request.

### 4.1 P8 follow-up: dedicated technical owners (proposal, Stage 7C)

This is a design proposal only, recorded in full in ADR-041. No ownership,
grant or policy has been changed. It would remove the run-time superuser
requirement of P8 for the functions listed, using the pattern of
`hid_ocr_queue_metrics` (0075) and `hid_event_delivery_commands`.

- **Functions and owners.** Five non-login, non-inherited, non-bypass roles:
  - `hid_ocr_worker_commands` owns the four worker commands (claim, renew,
    complete, fail), and the test-only wrappers `ocr.claim_next_job`,
    `ocr.record_extraction` and `ocr.fail_job` that call them;
  - `hid_ocr_job_guard` owns the five OCR insert and job guards
    (`validate_job_write`, `validate_extraction_insert`,
    `validate_validation_insert`, `validate_patient_confirmation`,
    `validate_publication_write`);
  - `hid_ocr_job_events` owns `record_job_event`;
  - `hid_document_scan_commands` owns `ehr.append_document_scan_event`;
  - `hid_outreach_campaign_guard` owns
    `outreach.validate_registration_campaign_write`.

  `ocr.worker_queue_metrics()` is already done. These are not all the
  definer functions involved: of the 175 that the migration administrator
  owns, 65 name a table with `FORCE ROW LEVEL SECURITY` and 101 name any table
  with row-level security, most outside these schemas. The other 36 name only
  identity tables with row-level security but no `FORCE` (`identity.patients`,
  `patient_identifiers`, `access_requests`, `consent_grants`,
  `consent_directives`, `consent_directive_versions`), whose policies do not
  apply to their owner but would apply to a technical owner. Each must
  pass `schema.integration.sql` and the runtime verifiers under the
  non-superuser owner before the requirement is dropped, or get a technical
  owner too.
- **Minimum privileges.**
  - Each role gets `USAGE` on its schemas, grants for the columns its
    functions read, insert or update, and `EXECUTE` on the helpers it calls.
  - The guards read whole rows (`select *`) of `ocr.jobs`, `ocr.validations`
    and `ocr.patient_confirmations`, so they need every column of those
    tables, unless the implementing migration rewrites those reads.
  - A row lock needs `UPDATE` on at least one column.
  - No role owns a relation, and no runtime role is granted a technical role.
- **Row-level security.**
  - Each role gets exact cross-facility policies `TO <role> USING (true)`,
    which is what today's superuser owner sees. The worker, the scanner and
    the job triggers inside worker transactions name no facility.
  - Locking roles get a `FOR UPDATE` policy.
  - A lock-only role also gets a restrictive `FOR UPDATE … WITH CHECK (false)`
    policy. A permissive one would not stop an update that an existing `PUBLIC`
    update policy admits.
  - `ocr.job_events` gets its first insert policy, for `hid_ocr_job_events`
    only.
- **`plpgsql.variable_conflict`.** A new migration replaces
  `ocr.claim_worker_job` with `#variable_conflict use_column` on the first
  line of its body and no 0015 setting. Verified locally on PostgreSQL 16.15:
  - a non-superuser-owned definer that applies 0015's `SET` fails with
    `permission denied to set parameter "plpgsql.variable_conflict"`;
  - the in-body option works under such an owner;
  - a non-superuser can replace the function this way, but cannot
    `ALTER FUNCTION … RESET` the setting.

  This does not let a non-superuser apply 0015 itself, which is also refused
  to it. A database migrated from 0001 by a non-superuser administrator, as on
  RDS, stops at 0015 unless that administrator holds `SET` on the parameter
  (`GRANT SET ON PARAMETER`, PostgreSQL 15 and later). The grant must then
  stay: `ocr.claim_worker_job` applies 0015's setting as its owner on every
  call, so OCR claims fail once it is revoked, until the in-body replacement
  ships. A superuser must grant it, or the RDS master if RDS allows it, which
  is unverified. This part of P8 stays open.
- **No superuser schema owner** (each point verified locally with a
  `NOSUPERUSER CREATEROLE` administrator):
  - the bootstrap must create roles with their attributes and check them, not
    `ALTER ROLE … NOSUPERUSER`;
  - transferring a function needs `SET` on the technical role, and `CREATE` on
    the schema for that role, granted and revoked around the transfer;
  - a later `CREATE OR REPLACE` of a technical-owned function runs as the
    technical role (`SET ROLE`), again with `CREATE` granted for that
    statement only.
  - An `INHERIT` membership would also work, but every technical policy would
    then apply to the migration administrator and to the definer functions it
    still owns. `runtime-roles.integration.sql` would allow exactly the
    administrator's `SET`-only memberships.
- **Migration, rollback, compatibility.**
  - Order: one behaviour-neutral migration (the claim body; explicit columns
    in the scanner command and, if chosen, in the guards), then the bootstrap.
  - No API, worker or contract change.
  - Rollback: return ownership to the migration owner and drop the technical
    policies.
  - The rehearsal's non-superuser owner check would also run
    `schema.integration.sql` and assert each owner. S1 repeats it on RDS.

### 4.2 Release blockers found in Stage 8 (fixed in Stage 9)

**Runtime roles could not run their own locking statements.** `SELECT ... FOR UPDATE` and `FOR SHARE` need `UPDATE` privilege on each locked table and, under row-level security, a matching `UPDATE` policy. The runtime roles have only `SELECT` and `INSERT` on most evidence tables, so these statements failed with `42501 permission denied for table ...` before any row was read, and the whole command failed (`5xx`). The defects date from the baseline; unit tests mock the database and no runtime verifier exercised these commands. Stage 9 fixes every path without a new `UPDATE` grant or policy (§2, ADR-042). Line numbers are those on `main` before Stage 9 (`54f79d2`).

| --- | --- | --- | --- | --- |
| Pharmacy: EHR prescription acceptance replay | `pharmacy.service.ts:77` `FOR UPDATE` | `pharmacy.work_items`, `hid_pharmacy_api_runtime` | No `UPDATE`; the table is append-only (trigger) | Lock removed; unique keys per prescription and per key |
| Pharmacy: dispense | `:144`, `:154` `FOR UPDATE` | `work_items`, `dispensings` | No `UPDATE`; append-only | Locks removed; one dispensing per work item |

A column-level `UPDATE` grant would not have helped: without an `UPDATE` policy, row-level security hides every row from the lock, so a replay would fall through as if nothing had been stored. Every row these statements locked and no longer lock is insert-only, so no transaction can change it after it becomes visible, with two exceptions: the Identity patient (the projection of the registration case, which is still locked, alone) and the Outreach campaign membership, which no API command changes or deletes and which the registration trigger locks as its owner. The mutable rows some of them also locked stay locked: the OCR job (taken first by every OCR command), the Outreach campaign (`FOR SHARE OF campaign`) and the Identity registration case. Of a row that cannot change, the lock serialized nothing that the unique constraints and `SERIALIZABLE` do not already decide: it cannot lock a row a concurrent request has not committed. The remaining locks of the services are on rows their runtime role may update (for example OCR jobs, Lab specimens, executions and results, Outreach campaigns and registration cases, Identity registration cases); `scripts/verify-runtime-locking-privileges.mjs` checks each one in CI.

## 5. Migration order and lock windows

1. Apply migrations in ledger order with `npm run db:migrate`. Every migration runs in one transaction with `lock_timeout 5s` and `statement_timeout 120s` (each statement), and a failed migration rolls back completely. Never edit an applied migration; checksums are verified.
2. **0067** adds `access_scope` with a `CHECK` to `audit.events`, then replaces three checks and validates them. This runs in one transaction under an `ACCESS EXCLUSIVE` lock, held to commit, with full-table validation scans. **Reads and writes of `audit.events` are blocked for the whole migration**, which stops nearly every audited request.
3. **0069** drops and re-adds validated `CHECK` constraints on `auth.sessions` and `auth.session_events` under `ACCESS EXCLUSIVE`. Sign-in, refresh and session checks wait while it scans.
4. **0072 builds `audit_resource_uuid_sequence_idx` without `CONCURRENTLY`.** This is possible only inside the runner's transaction. The build holds a `SHARE` lock on `audit.events`:
   - every audited write waits until the build finishes, and that includes most authenticated requests;
   - reads continue.
5. Each of these statements must finish within 120 s, or its migration rolls back and nothing changes. The 5 s `lock_timeout` also fails a migration that cannot get its lock, so stop traffic to Identity, or keep it low, during the window. Measured locally for 0072 only (Stage 5, PostgreSQL 16, synthetic rows, development container, not production hardware): over 1,000,000 audit rows (414 MB, two thirds with a UUID target), the index statement ran in 1.1 s under the runner's settings and produced a 35 MB index. 0067, 0069 and 0074 (step 7) were not measured. Measure all four in the staging rehearsal (S1), scale by the P5 sizes with a wide margin for production I/O, and size the window on the combined cost.
6. **0073** replaces two functions and adds one. It takes no table lock and needs no window. At run time, each session revocation, sign-out and expiry holds its account row lock until it commits, usually milliseconds. Sign-ins, refreshes and sign-outs of that one account wait for that long. Once every Identity instance runs Stage 5B, every path that revokes sessions takes the account row before any session row, so they cannot deadlock with each other. Pre-existing, and unchanged: two administrators changing each other's accounts at the same moment (status, platform role) can deadlock, because each command locks its target and then references its actor. A session revocation can join that cycle when the target's account id sorts before the actor's. PostgreSQL cancels one command, which fails and can be retried; nothing is half applied.
7. **0074** has two effects:
   - It builds `consent_grants_request_idx` without `CONCURRENTLY`, under a `SHARE` lock on `identity.consent_grants`. New grants wait until the build finishes, that is, a patient's approval and a clinician's PIN access. Reads continue. Not measured; measure it with the others in S1.
   - It drops and recreates `identity.list_my_staff_access_requests(text)`, because its result type changes.
8. **0075** creates `ocr.worker_queue_metrics()` (no table lock) and the policy `ocr_outbox_staff_insert`. `CREATE POLICY` takes an `ACCESS EXCLUSIVE` lock on `ocr.outbox_events` for the catalog change only. It waits for in-flight OCR transactions on that table within the 5 s lock timeout. The bootstrap likewise recreates `ocr_jobs_queue_metrics_read` on `ocr.jobs` under a brief `ACCESS EXCLUSIVE` lock, as it already does for the outbox delivery policies.
9. **0076** replaces the trigger functions `ocr.validate_patient_confirmation()` and `ocr.validate_validation_insert()` (`CREATE OR REPLACE`) and creates `auth.lock_account_for_mfa(uuid)`. It takes no table lock and needs no window; an OCR confirmation or validation in flight keeps the definition it started with.
10. **0077** replaces 18 functions (`CREATE OR REPLACE`): two OCR worker commands, the OCR job, job-event and publication triggers, and the Lab, Pharmacy and Outreach guards. It takes no table lock and needs no window. Run P9 first.
11. **0078** drops the policy `patient_identifiers_self_nin_insert` on `identity.patient_identifiers` and replaces `lab.validate_work_item_child()` (`CREATE OR REPLACE`). The policy change takes an `ACCESS EXCLUSIVE` lock on `identity.patient_identifiers` for the catalog change only, waiting for in-flight transactions on that table within the 5 s lock timeout; no table is scanned or rewritten.
12. **0079** (D-Eminence/hid-system#45) replaces `identity.access_patient_with_pin(text, text, integer)` (`CREATE OR REPLACE`). It takes no table lock, needs no window, no bootstrap and no service change. A PIN check in flight keeps the definition it started with. From then on a correct PIN no longer clears the actor's failure window, so a clinician who mistypes PINs for several patients within 15 minutes can reach the 15-minute actor lock (`DATABASE.md`, "Patient access PIN actor window (0079)").
13. **0080** (D-Eminence/hid-system#48) replaces `pharmacy.validate_work_item()` and `pharmacy.validate_dispensing()` (`CREATE OR REPLACE`). It takes no table lock, needs no window and no bootstrap. A Pharmacy command in flight keeps the definition it started with. At run time a dispense or acceptance takes `FOR SHARE` on its EHR prescription row, so an EHR prescription update waits for an in-flight dispense or acceptance, milliseconds. Deploy the Pharmacy API with the `409` mapping before or with it; the EHR API order is unchanged (§3, §6).
14. If any estimate approaches 120 s, stop and re-plan before the release. 0072 cannot be edited or worked around in place: an index built beforehand under the same name makes 0072 fail. Do not raise the timeouts ad hoc.
15. **Immediately after the migrations, run `npm run db:bootstrap`, then `npm run db:verify-roles`.**
   - 0072 drops and recreates `audit.list_platform_events` with eleven arguments. Until the bootstrap grants `EXECUTE` on the new signature, any running Identity is refused on the platform audit list.
   - The bootstrap grants `EXECUTE` on `identity.list_my_staff_access_requests(text)` to the Identity runtime (D-Eminence/hid-system#26). Before that grant existed, the clinician list was refused (`403`) everywhere. 0074 recreates the function, so after 0074 the list is refused for every Identity build until the bootstrap runs.
   - The bootstrap grants `EXECUTE` on `auth.lock_account_sessions(uuid)` (0073) to the Identity runtime. A Stage 5B Identity running before this, or before 0073, fails with a database error (`5xx`) on every sign-out, every refresh of an expired session, an administrator's own-session revocation and refresh-token reuse; a reused family is then not revoked. Earlier Identity builds do not call it.
   - Between this step and step 6, and during a rolling Identity deploy, an earlier Identity runs against 0073. Its sign-out, expired refresh, refresh-reuse revocation and own-session revocation lock session rows before the account row, so each can deadlock with an administrator's revocation of the same account at the same moment. PostgreSQL cancels one of the two, which fails with an error and can be retried (§9). Keep that interval short.
   - The bootstrap creates `hid_ocr_queue_metrics`, makes it the owner of `ocr.worker_queue_metrics()`, creates its policy and grants the OCR worker `EXECUTE` (0075). Until then a Stage 6 worker logs `ocr.queue.metrics_unavailable`, as every worker does today.
   - The bootstrap grants `EXECUTE` on `auth.lock_account_for_mfa(uuid)` (0076) to the Identity runtime. A Stage 7 Identity running before this, or before 0076, fails every platform MFA transaction with a database error (`5xx`). Earlier Identity builds do not call it.
   - The bootstrap grants `EXECUTE` on `auth.account_id_for_subject(text)` to the Outreach runtime (Stage 8). Until then every Outreach write fails with `42501`, as it always has.
   - The bootstrap also runs the runtime-role assertions. From Stage 9 they require 0078 (no self-NIN insert policy), so run the Stage 9 bootstrap and `db:verify-roles` only after 0078.

## 9. Rollback and recovery

- **Migrations are forward-only.** There are no down migrations. Recovery from a failed migration needs no action, because the transaction rolls back. Recovery from a wrong but successful migration is a restore from P2. Practise it in staging (S6) before relying on it.
- **Identity after 0072:**
  - The previous Stage 4A build runs unchanged, because Stage 5 has no schema change.
  - A pre-4A build also runs. Its nine-argument audit call resolves to the new function through the defaulted arguments; `platform-admin-contracts.integration.sql` checks this.
  - **Do not roll the console back below Stage 4B while Identity is at Stage 4A or later (§3).**
- **Identity after 0073:** Stage 5 and earlier builds run unchanged. The two admin commands keep their contracts, and only Stage 5B calls the new helper. Rolling Identity back to Stage 5 removes the lock from the reuse, own-session, sign-out and expiry paths. The two admin revocations keep it, because it is in the database. With that combination, any of those four paths at the same moment as an administrator's revocation of the same account can deadlock. PostgreSQL then cancels one of the two. Either the sign-out or refresh fails with a `5xx` (reproduced locally, §8), or the administrator's revocation fails and must be retried. Prefer rolling forward.
- **Identity after 0074:** once the bootstrap has run, earlier builds keep working (§3); roll Identity back freely. The new index and the new result columns stay. Rolling back the Health-id portal only hides the outcomes.
- **Identity after Stage 7:** roll back freely; 0076's helper stays and earlier builds do not call it. A Stage 6 or earlier Identity brings back the deadlock between an approved MFA reset and an MFA transaction of the same account (§2): PostgreSQL then cancels one, and either the MFA request fails with a `5xx` or the approval fails and must be retried. It also lets parallel second-factor attempts of one account exceed the failure limit again.
- **0076:** forward-only like every migration. To restore the earlier guard bodies, a new migration would have to recreate them; that would accept a confirmation for any patient again under a non-bypass owner, and validations from sessions without an account or membership. No OCR build depends on the earlier behaviour. The Stage 7 Identity needs `auth.lock_account_for_mfa`.
- **0077:** forward-only. Restoring the earlier bodies would need a new migration and would bring back the NULL claim token, the refused lease renewals, jobs for unscanned documents, publications attributed to any member and the NULL-session gaps of the Lab, Pharmacy and Outreach guards. No service build depends on the earlier behaviour. Revoking the Outreach grant would stop every Outreach write again.
- **0078:** forward-only. Restoring the earlier policy or trigger would need a new migration and would stop every Identity runtime insert of a patient identifier, including the NIN registration reviews (`42501`), and every Lab acceptance of an EHR order (`42703`) again. No build depends on the earlier definitions.
- **Pharmacy, Lab, OCR, Outreach and Identity after Stage 9:** rolling any of them back to an earlier build restores its §4.2 failure (`500` on every affected command) and nothing else; 0078 stays and harms no earlier build. Rows written by the Stage 9 builds stay valid.
- **0079:** forward-only. Restoring the 0033 body would need a new migration and would bring back the bypass: a correct PIN for one patient would again clear the actor's failures at others. No service build depends on either behaviour.
- **0080:** forward-only. Restoring the 0077 bodies would need a new migration and would let Pharmacy accept cancelled or nonexistent prescriptions and dispense work whose prescription was cancelled again. Rolling the Pharmacy API back keeps the refusals and answers them with `500` instead of `409`. Rolling the EHR API back is safe: 0080 does not compare the prescription time or dates, so the earlier EHR's millisecond time is accepted (§3), and day-early dates from an EHR process east of UTC are stored as before 0080. Once a later release compares the time and dates exactly, an EHR build before this change can no longer hand off: that release must record the EHR rollback floor.
- **OCR after 0075:** roll the OCR API and worker back freely. Earlier workers lose the metrics again; earlier APIs write the earlier, possibly unlinked, events. The function, the role and both policies stay. Removing the outbox insert policy would stop patient confirmation and publication again.
- **Delegated cookie reads (#38):** code only, no persisted state. Rolling back Identity brings back the `403 ORIGIN_DENIED` refusal for the same-origin cookie reads of all four services (EHR, Lab, OCR and Pharmacy). Rolling back EHR brings it back for EHR's and OCR's cookie reads (OCR reads each job's source document through EHR); rolling back Lab, OCR or Pharmacy brings it back for that service only (§3). Nothing else of #38 changes; an EHR API rolled back past the paging fix also loses that fix (next entry).
- **Outreach cookie reads (D-Eminence/hid-system#43):** code only, no persisted state. Rolling back either Outreach or Identity brings back the refusal of Outreach's same-origin cookie reads: `403 CSRF_VALIDATION_FAILED` from an earlier Outreach, `403 ORIGIN_DENIED` from an earlier Identity (§3). Rolling back Identity also brings back `400 VALIDATION_FAILED` on the two campaign reads for bearer requests (a same-origin cookie read is already refused `403`, as above). The three campaign writes answer `400 VALIDATION_FAILED` with either Identity, so a rollback changes nothing for them. Registration-case writes are unaffected.
- **EHR to Lab order time (#44):** code only; no schema or grant change. Rolling the EHR API back brings back Lab's refusal (`500`, SQLSTATE `23514`) of almost every new EHR order acceptance. Work items Lab accepted from the new build keep a digest over the microsecond text, so a same-key replay of one of those orders through the earlier build gets `409 IDEMPOTENCY_CONFLICT`; Lab keeps the work item (§3).
- **EHR clinical list paging:** code only, no persisted state. Rolling the EHR API back brings back the rows skipped within a millisecond. Cursors issued by either build are refused by the other with `400 INVALID_CURSOR`, after which Health-id reloads the first page (§3).
- **Refresh-event change:** this is code only. Rolling back Identity brings back the old misclassification and nothing else. Existing `refresh`/`denied` events remain valid rows.
- **Session-route refusal audits:** code only. Rolling Identity back brings back the `503` for a staff refusal on a session route, and returns patient and anonymous sign-out refusals there to `api.*` rows. The `auth.*` failure rows it wrote remain valid rows.
- **Sign-out and client kind (#39):** code only. Rolling Identity back brings back the idle sign-out that answers `401` and leaves the sign-in live, and removes the client-kind check and the `x-hid-client` CORS entry. `logout` events marked `presented: refresh_token` remain valid rows.
- **EHR and OCR guard refusals before a facility is bound (#46):** code only, no persisted state. Rolling the EHR or OCR API back brings back the `503 DEPENDENCY_UNAVAILABLE` answer, with no audit row, for those refusals, and in EHR the `401 AUTHENTICATION_REQUIRED` answer to a patient whose control check hits a database fault. `auth.authorization.denied` rows already written stay valid.
- **Released Lab results:** code only. Rolling the Lab API back returns unreleased correction values to released-only history readers again, removes the order route (`404`) and stops the read audit events. Audit rows already written remain valid.
- **MFA key:** if `MFA_SECRET_KEY_B64` is lost, every enrolled authenticator must be re-enrolled. Store it with the same care as the field-encryption keys.
- **Identity MFA key in the task definition (D-Eminence/hid-system#49):** infrastructure only. Rolling the regional stack back to a task definition without the reference brings back `503 MFA_UNAVAILABLE` for every platform sign-in and changes nothing else; enrolled authenticators work again once the same key and `aws-v1` return. Keep the `mfaSecretKeyB64` field for as long as any deployed task definition references it: ECS resolves it whenever it starts an Identity task (deployment, scaling, replacement). Never change the key or the version to roll back.
- **Lockout:** if every Super Admin is locked out (lost authenticators and recovery codes), recovery needs the documented break-glass procedure. That procedure is not built yet; see the product decisions in `PHASE_4_STAGE_4A_ADMIN_CONTRACTS.md` §9. Keep two independent Super Admins with stored recovery codes.

**Known limits of Stage 6:**
- Queue metrics are emitted with each claim. A worker that claims nothing (stopped, stalled, wrong provider, ineligible documents) emits none, and `treatMissingData` is `NOT_BREACHING`. So `OcrQueueAgeAlarm` cannot detect a stopped worker, and `OcrDrainRateAlarm` cannot breach. Fixing this needs two changes, both out of scope here:
  - an OCR worker change to log a separate, periodic queue-metrics event from `ocr.worker_queue_metrics()` (it cannot reuse `ocr.job.claimed`, whose `claimedJobs` feeds the throughput metric);
  - matching metric filters in `infra/aws`.
- The OCR worker's own database audit events (`ocr.worker.claim`, `ocr.worker.complete`, `ocr.worker.fail`, `ocr.worker.lease_recovered`) still carry `ocr.jobs.patient_id`, so for a job created without a patient they remain unlinked.
- The age is time since the earliest `queued_at`, as before. A job retried by the worker keeps its first `queued_at`, so the age includes earlier attempts and back-off.
- Replays of idempotent OCR writes return the stored result without a new read event; the original write event remains.

**Lock-order hazards:** the MFA reset hazard recorded here until Stage 6 is fixed by Stage 7A (§2). These pre-existing hazards remain; none involves an MFA authenticator. In each, PostgreSQL cancels one command, which fails and can be retried; nothing is half applied:
- two administrators acting on each other's accounts at the same moment. A status change, a platform role change, an approval request or an approval decision locks its target's account row and then references its actor's (the idempotency row, `requested_by`, `decided_by`, `revoked_by`, the audit event). A session revocation joins the cycle when the target's account id sorts before the actor's (§5, step 6);
- a new approval request and a decision on an earlier request for the same target and action, exactly as that earlier request expires;
- an OTP password-recovery resend and the completion of the same recovery: the resend locks the open challenge and then inserts a new one (a `FOR KEY SHARE` on the account), while `auth.complete_recovery_otp` locks the account and then that challenge. It needs the resend cooldown to have passed while the challenge is still open.

Each would be fixed the same way: lock every account involved, in account order, before anything else. Stage 8 reproduced all three locally as real deadlocks (`40P01`, `pg_stat_database.deadlocks` +1 each), running the Identity API's own transactions as a login of the Identity runtime on a 0076 copy:
- two Super Admins disabling, or granting roles to, each other; an approval of an MFA reset of B while B requests one for A; and a revocation of A's sessions by B while A disables B. Sent in the same event-loop tick, two role changes deadlocked in 78 of 200 runs; 0.5–1 ms apart, in 1–2 of 100; 2 ms apart, never. The cancelled side gets `503 ADMIN_COMMAND_UNAVAILABLE`, wrote nothing (no idempotency or audit row) and can be retried with the same key. Which side is cancelled depends on timing: in two runs it was a Super Admin's revocation of a compromised administrator's sessions, which then stayed live until retried;
- a decision landing within milliseconds of its request's expiry while a new request for the same target and action arrives: either side may be cancelled; an expired request never executes;
- an OTP recovery resend between the completion's account lock and its challenge lock: the cancelled side answers `500` instead of `403` or `202`;
- a fourth hazard, not listed before: a Super Admin suspending or rejecting a verified facility (`identity.admin_transition_facility`, 0072, which takes the last-Super-Admin advisory lock and then references its actor's account) while another disables that Super Admin or revokes their Super Admin role (which lock the target account and then take the same advisory lock). Reproduced: the disable was cancelled and left nothing.

A prototype on a copy (the 0073 ordered account lock in `auth.admin_transition_account`, `auth.admin_change_platform_role`, `auth.admin_request_approval` and `auth.admin_decide_approval`, the latter reading the request's target unlocked first, and `auth.lock_account_for_mfa` in `OtpService.start`) removed those deadlocks, 0 of 200 in the same-tick test, and the existing suites passed. An independent check then found that it does not fix the facility hazard and opens a new cycle: two concurrent requests of one administrator, one suspending a facility and one disabling another Super Admin, deadlock with each other (reproduced; they do not on the current code). It is not in Stage 8: each hazard is fail-safe and needs two administrators or a recovering user acting within about a millisecond, while the fix rewrites the two-person approval and last-Super-Admin commands and needs two-connection race tests. A command that waited for its actor to be disabled or signed out also proceeds or fails on the audit trigger (`503`) instead of `403`; re-checking the actor's permission after the lock belongs with that change.

**Known limits of Stage 7B**, all closed by 0077 (§2): the OCR job trigger's scan comparison for inserts, source changes and starts of processing, the NULL claim token of the OCR worker commands, the Lab OCR-import guard's unchecked lookups, the thirteen Lab, Pharmacy and Outreach guards that compared the session with `<>`, and the unbound OCR publication requester. For the twelve guards whose coverage had not been checked, row-level security refuses a NULL session for the runtime roles (reproduced locally); the guards themselves now refuse it too.

**Known limits of Stage 9.** None is introduced by Stage 9; each was hidden behind the §4.2 failures:
- A unique conflict that a retry cannot resolve still answers `500`, after one retry: two members verifying or releasing one Lab result version, at once or one after the other (`result_verifications` / `result_releases` unique keys), a second result entry for one Lab execution under a new key (`results_execution_id_key`), a prescription, EHR order or OCR publication already accepted or imported in another facility (hidden from the replay read by row-level security), and keys reused across targets in some commands. Mapping these constraints to `409` is a follow-up; for the cross-facility case it must decide what a `409` may disclose.
- Contention costs latency. Concurrent writes on small tables cancel each other under `SERIALIZABLE` even when they touch different rows; the retry lets them through one by one, so under a burst a request can take several attempts (9 at most in the local measurements, the shipped policy included). Pharmacy dispense and reverse, the Lab accession, specimen, execution and result commands and the OCR validation, confirmation and publication requests call Identity (and OCR also the EHR) inside their transaction, which lengthens every attempt, and each attempt repeats that call, which Identity audits (`identity.authorization.check`); each OCR attempt also reads the source document from the EHR, which records a patient-linked `ehr.document.ocr-source.read` event and EHR's own Identity check, so an access report built from the audit trail can count one OCR command several times. Lab writes that audit on a second connection of its pool while the transaction holds the first, so a burst of as many Lab commands as the pool has connections (`DATABASE_POOL_MAX`) can stall until the 5 s connection timeout and answer `503`; accession creation reaches this since Stage 9, the specimen, execution and result commands did before. Authorizing before the transaction, as Pharmacy acceptance and import, Lab import and Outreach already do, is the recommended follow-up. As the tables grow, their index pages split and fewer unrelated requests collide.
- Pharmacy, Lab and Outreach replays match the stored row by its target (prescription, work item, dispensing, publication), not by actor and key, so a second member who sends an identical body with another key receives the first member's row as a replay, after passing the same authorization. The Lab accession replay read can match two rows (one by work item, one by key) and then answers a replay or `409` depending on plan order.
- OCR publication: only `OWNING_SERVICE_UNAVAILABLE` and `REQUEST_IN_PROGRESS` count as retryable failures, for a later request and for the claim alike. A failure that is not a `4xx` refusal (an owning domain's `5xx`, a timeout, a lost connection, or an error inside the attempt) is stored as `OWNING_SERVICE_UNAVAILABLE`, and the code it arrived with stays in `failure_summary` and in the audit event's `ownerFailureCode`: either the owning domain's own code (the Lab API's default code for a `503` is `DEPENDENCY_UNAVAILABLE`), or the code OCR's integration gives a call that got no answer (`LAB_SERVICE_UNAVAILABLE`, `EHR_SERVICE_UNAVAILABLE`, `PHARMACY_SERVICE_UNAVAILABLE`, `IDENTITY_SERVICE_UNAVAILABLE`). A retryable failure can be claimed again 15 s later, up to `max_attempts` (3) attempts, so an owning domain's `5xx` that is not transient also uses every attempt; this trade-off comes with the retry fix (§8), where such a failure was terminal at once. After the last one a publication answers `409 OCR_PUBLICATION_IN_PROGRESS`, not `409 OCR_PUBLICATION_TERMINAL`, and no operator path retries it. A retry repeats the original request with its `Idempotency-Key`; the EHR review workspace keeps that key only while it stays open, so after a reload its Retry answers `409 OCR_ALREADY_PUBLISHED` (a frontend follow-up). A `4xx` refusal other than `REQUEST_IN_PROGRESS` stays terminal under the owning domain's code. In JWT workload-identity mode, the Identity, EHR, Lab and Pharmacy APIs each answer `401` when they cannot verify the caller's token, and a failure to fetch their JWKS is such a failure (`workload-auth.service.ts` in Identity, `ocr-internal-caller.guard.ts` in EHR, `lab-workload-identity.service.ts`, `pharmacy-workload-identity.service.ts`). Every attempt asks Identity and reads the source document from EHR, so a JWKS outage at any of them ends a publication as terminal; answering `503` for it is a follow-up in those services.
- Some refusals by the database still answer `500` where the service has no mapping, for example a Lab member verifying a result they entered (`23514 Result verifier must be independent`; nothing is written, and Stage 9 makes the Lab result path reachable for the first time), a row-level security refusal when Identity allowed a request the database does not, or an Outreach trigger refusal reached in a race (`42501`, `23514`).
- Outreach campaign registration requires `outreach.campaign.write` (§3). Deactivating that permission also stops campaign-linked registration.
- Lab orders created on the EHR while Lab acceptance failed have no work item (§10).
- Lock-order hazards: Stage 9 changed one (the OCR publication cycle, §2, fixed and race-tested). The administrator lock-order hazards below are unchanged. Every service write takes `FOR KEY SHARE` on its actor's account, membership and facility rows through foreign keys, which an administrator command locking those rows `FOR UPDATE` waits for or makes wait; the Stage 9 mapping found no cycle with them, because no service write locks an identity row first.
- P8: OCR patient confirmation and campaign-linked Outreach registration still depend on a schema owner that can read row-level-secured rows (§4).
- Identity NIN resolve (`POST /identity/nin/resolve`, not a locking path): the service recognises a duplicate request by the constraint name `registration_cases_facility_id_created_by_account_id_idempotency_key_key`, but PostgreSQL truncated that name to 63 bytes (`..._idempo_key`, 0011). The loser of two concurrent identical resolve requests therefore gets `500` instead of the replay. Found by the Stage 9 mapping; a follow-up.

**Known limits of Stage 8:**
- Twelve Identity definer functions gate on `platform.current_actor_subject() <> 'system:auth'`, which passes when the session has no subject, and two compare a stored enrollment token HMAC with `<>` against the caller's, which passes for a NULL argument (`identity.activate_public_patient_enrollment`, `auth.bind_google_onboarding_capability`). Only the Identity runtime can execute them, it may set `system:auth` itself, and the Identity API always passes a computed HMAC; defence in depth for a later stage.

So, under a session that bypasses row-level security: the Pharmacy work-item event guard still does not compare the facility; the Outreach event guard compares neither the facility nor the purpose; the Outreach campaign guard never compares the purpose, and its update branch compares only the facility, so a campaign's status can change with no account in the session. Each is a follow-up.

**Known limits of the delegated cookie-read fix (#38):**
- Identity cannot check the reported method. Any approved workload caller with valid credentials can have the cookie Origin and CSRF check skipped on the patient authorization check by reporting `GET`, `HEAD` or `OPTIONS`. A real browser write is still checked first: EHR, Lab, OCR and Pharmacy revalidate the session through `POST /auth/service-session` (Outreach checks writes in `outreach-security.guard.ts` and through `POST /identity/outreach/authorize`, which #38 does not mark; the Outreach cookie-read branch marks it, and after a reported read it then authorizes only a read permission). The reported method is the method of the request the service is serving: for a service hop that forwards the user's cookie, such as OCR's `GET /api/v1/ehr/internal/ocr/documents/:documentId/source` during job creation, EHR reports that hop's `GET`, after OCR has already revalidated the originating browser write.
- Before D-Eminence/hid-system#43, Outreach's own guard (`outreach-security.guard.ts`) required an allowed Origin and an `X-CSRF-Token` on every cookie request, `GET` included, and refused it otherwise with `403 CSRF_VALIDATION_FAILED`. A same-origin browser `GET` carries no Origin, and neither the Cloudflare frontend worker (`infra/cloudflare/src/frontend-worker.mjs`) nor the gateway (`gateway/proxy-headers.conf`) adds one. Health-id also sends `X-CSRF-Token` only on writes (Health-id `packages/http/src/client.ts`). Same-origin cookie reads from Outreach were therefore refused. This was first recorded from reading the code; it has since been reproduced locally over HTTP, together with the two Identity refusals behind it, and all three are fixed by the Outreach cookie-read change (D-Eminence/hid-system#43; §2, ADR-045).
- The HTTP verifier covers EHR only (§8).

**Known limits of the Outreach cookie-read fix (D-Eminence/hid-system#43):**
- As with #38, Identity cannot check the reported method and relies on the authenticated workload. After a reported read, `POST /identity/outreach/authorize` authorizes only a read permission, so a misreported method can authorize an Outreach read but not a write.
- Campaign writes stay closed: Identity refuses `outreach.campaign.write` with `400 VALIDATION_FAILED`, as on `main`, so no campaign can be created through the API and S4c's campaign create cannot pass (§7). Who may create campaigns, change their status and add members is an open product decision (§2, ADR-045). Health-id's Outreach page can list campaigns and members, but its campaign create, status and member actions get `400`; Health-id should hide or handle them.
- Campaign-linked registration works as the runtime role since D-Eminence/hid-system#34, but only for a campaign that already exists, and none can be created through the API while campaign writes stay refused.
- The evidence is local and synthetic: the HTTP verifier and the unit specs (§8). No browser run covers Outreach cookie reads.

**Known limits of the released Lab results change:**
- Any member holding `lab.result.released.read` with a `read_records` consent grant for the patient at the facility reads an order's released results, not only the clinician who placed the order; this is the same patient-level authorization as every other clinical read.
- A clinician is not told that a correction is pending release, and is not notified of a release: nothing in the EHR consumes `LabResultReleased`, so the result appears only when the order route is read.
- Released revisions keep their stored version numbers, so a gap (versions 1 and 3) shows that an intermediate revision was never released; its value and reason are not returned.
- Break-glass reads are allowed, as for every Lab read, until the break-glass scope of Lab and Pharmacy reads is decided.

**Pharmacy work no longer dispensable (0080).** After 0080, an accepted work item without a dispensing whose EHR prescription is missing, no longer `active`, at another version, or of another patient, facility or encounter answers `409 PHARMACY_PRESCRIPTION_NOT_DISPENSABLE`, and Health-id still offers its dispense form. List them with the read-only query below, as the migration administrator, and tell the pharmacies concerned; a changed prescription needs a new EHR prescription and handoff (§2). The query was written for this change and has not been run against a database.

```sql
begin transaction isolation level repeatable read read only;
set local statement_timeout = '120s';
set local lock_timeout = '5s';
set local row_security = off;
select item.id as work_item_id, item.facility_id, item.patient_id, item.source_ehr_prescription_id,
       item.source_ehr_prescription_version, prescription.status, prescription.row_version, item.accepted_at
  from pharmacy.work_items item
  left join ehr.prescriptions prescription on prescription.id = item.source_ehr_prescription_id
 where not exists (select 1 from pharmacy.dispensings dispensing where dispensing.work_item_id = item.id)
   and (prescription.id is null
        or prescription.status is distinct from 'active'
        or prescription.row_version is distinct from item.source_ehr_prescription_version
        or prescription.patient_id is distinct from item.patient_id
        or prescription.facility_id is distinct from item.facility_id
        or prescription.encounter_id is distinct from item.source_encounter_id)
 order by item.accepted_at, item.id
 limit 500;
rollback;
```

**Lab order reconciliation (Stage 9).** The EHR commits a lab request, then calls Lab acceptance. Until Stage 9, 0078 and the EHR to Lab order-time fix (§2), every acceptance (almost every, after Stage 9 alone) failed, so on any environment where the EHR API created active lab requests, those requests have no Lab work item. A retry of the same EHR request with the same Idempotency-Key re-sends the acceptance while the request is active, at any time (the replay does not check the key's `expires_at`); nothing else does: an update of the request does not, including resuming an on-hold request or activating a draft. After the release, list them with the read-only check below, as the migration administrator, and decide with the clinical owners whether to re-send each one (a new EHR order, or a reviewed backfill under change control) or record why not. The check also lists completed requests without a work item: the EHR completed them although Lab never received them, so review each clinically (where was the test done, and is its result recorded?). Verified locally on synthetic data: it lists an active, an on-hold and a completed request without a work item, and not an active one with a work item or a draft or cancelled one. Pharmacy acceptance is an explicit pharmacist command that can simply be repeated.

```sql
begin transaction isolation level repeatable read read only;
set local statement_timeout = '120s';
set local lock_timeout = '5s';
set local row_security = off;
select request.id as lab_request_id, request.status, request.facility_id, request.patient_id, request.row_version,
       request.created_at
  from ehr.lab_requests request
 where request.status in ('active', 'on_hold', 'completed')
   and not exists (select 1 from lab.work_items item where item.source_ehr_order_id = request.id)
 order by request.created_at, request.id
 limit 500;
rollback;
```
